# 0160. E2E 데이터 초기화: Flyway 이력을 뺀 모든 테이블을 한 트랜잭션에서 비우고 시드 파일을 다시 실행한다. 시드 실행은 운영 코드 한 곳에 둔다

- 상태: 에이전트 결정
- 날짜: 2026-11-28
- 결정한 사람: 에이전트(Issue #59 '에이전트가 정하는 것': 초기화 구현, 클래스 구조, 테스트 방법)
- 관련: Issue [#59](https://github.com/Rasit-NP/curtain-call/issues/59), 결정 [0016](0016-integration-test-base.md), [0036](0036-seed-accounts.md),
  [0049](0049-performance-seed.md), spec 2.5, 6.9

## 결정

- **구조**: `testsupport` 기능에 `api.TestDataResetController`(`POST /api/test-support/reset`, `204 No Content`), `application.TestDataResetService`,
  `infra.SeedScripts`를 둔다. 컨트롤러와 서비스 모두 `@Profile("e2e")`다.
- **비우는 범위**: 현재 스키마에서 Flyway 이력 테이블을 뺀 모든 테이블을 `TRUNCATE ... RESTART IDENTITY CASCADE`로 비운다. 테이블 목록은 `pg_tables`에서 읽는다.
  선점·예매·결제·멱등 기록뿐 아니라 시드가 넣는 계정·공연장·배치·공연·좌석도 비운다.
- **시드 다시 넣기**: `classpath:db/seed/*.sql`을 파일 이름의 버전 번호 순서로 직접 실행한다. Flyway 이력은 건드리지 않는다.
- **한 트랜잭션**: 비우기와 시드 실행을 한 트랜잭션에서 한다.
- **id**: `RESTART IDENTITY`라 초기화 뒤 id가 처음과 같게 나온다. 그래도 E2E와 테스트는 이것을 가정하지 않는다(spec 6.9).
- **시드 실행 코드는 한 곳**: 테스트 도우미 `support.SeedFiles`에 있던 '버전 번호 순서로 실행' 코드를 운영 코드 `SeedScripts`로 옮기고, `SeedFiles`는 그것을 부른다.
  시드 통합 테스트(`E2eProfileAuthTest`, `PerformanceSeedTest`)와 초기화가 같은 코드로 시드를 넣고, 순서 테스트(`SeedFilesTest`)는 그대로 이 코드를 검증한다.
- **테스트**
  - `TestDataResetApiTest`(test 프로필에 e2e를 더함): 테이블을 비운 뒤 시드를 넣은 처음 상태의 시드 내용을 id가 아니라 이름(아이디, 공연장 이름, 공연 제목·일시, 좌석 표시 이름)으로 기억한다.
    선점·결제(승인과 거절)로 데이터를 만들고, 시드를 바꾼다(시드에 없는 계정·공연장·공연·좌석을 더하고, 모든 계정의 비밀번호와 공연 제목을 바꾸고, 남은 빈 좌석을 모두 SOLD로).
    초기화한 뒤 시드가 넣지 않는 테이블(Flyway 이력 제외)이 모두 비었는지, 시드 내용이 처음과 같은지 본다. 두 번 연달아, 시드가 없는 빈 DB에서, 로그인, 시드 조건(2.5)도 본다.
    '비었다'는 확인이 헛돌지 않게 초기화 전에 선점·결제 테이블에 행이 있는지, 시드가 넣는 테이블이 테스트가 아는 다섯 개뿐인지도 확인한다.
  - 등록 조건: 통합 테스트의 test 프로필 컨텍스트에 두 빈이 없는지(`TestDataResetRegistrationTest`), DB 없이 두 클래스만 등록하는 작은 컨텍스트로 local·test·prod·프로필 없음에서
    등록되지 않는지(`TestDataResetProfileTest`) 본다. e2e에서 등록되는 것은 `TestDataResetApiTest`가 실제 컨텍스트로 본다.
  - `E2eProfileAuthTest`의 '토큰 없이 부를 수 있다'는 컨트롤러가 없을 때 404를 기대했다(이름에 '컨트롤러가 없으면 404'). 컨트롤러가 생기면서 명세 6.9와 Issue 완료 조건대로 204를 기대하게 바꿨다.

## 근거

- 명세 6.9는 "데이터를 비우고 시드를 다시 넣는다", Issue는 "선점·예매·결제·멱등 기록을 비우고, 좌석 상태와 계정·공연 시드를 처음 상태로 되돌린다"고 정했다.
  시드 테이블까지 비우고 다시 넣으면 바뀐 시드 값이나 더해진 행이 남지 않는다.
- 테이블 목록을 DB에서 읽으면 새 기능의 테이블이 생겨도 빠지지 않는다. 통합 테스트의 테이블 비우기(결정 0016)와 같은 방식이다.
- 한 트랜잭션: `TRUNCATE`는 테이블을 배타적으로 잠가, 다른 요청은 빈 상태를 보지 못하고 초기화가 끝나기를 기다린다. 시드가 실패하면 비운 것도 되돌려진다.
- Flyway는 이미 적용한 버전 마이그레이션을 다시 실행하지 않는다. 시드 파일을 직접 다시 실행하는 것은 결정 0036·0049가 미리 정한 방향이다.
- 시드 실행 코드가 운영과 테스트에 따로 있으면 순서 규칙(버전 번호를 숫자로 비교)이 둘로 갈린다.

## 고려했지만 고르지 않은 것

- Flyway `clean` 뒤 `migrate`: 스키마를 지웠다 다시 만들어 느리고, `clean`을 켜야 한다(잘못된 DB에 붙으면 스키마까지 지운다).
  떠 있는 연결이 준비해 둔 문장이 다시 만든 테이블과 어긋날 수도 있다.
- 선점·결제 기록만 지우고 좌석을 UPDATE로 되돌리기: 바뀐 시드 값과 더해진 행이 남는다. 이 변형으로 테스트를 돌리면 `TestDataResetApiTest` 8개 중 7개가 실패했다(204만 보는 테스트만 통과).
- 비울 테이블을 코드에 적기: 새 테이블을 빠뜨릴 수 있다.

## 적용과 남은 점

- 코드: `backend/src/main/java/com/curtaincall/testsupport/`, `backend/src/test/java/com/curtaincall/testsupport/`, `support/SeedFiles`(위임).
- 마이그레이션이 직접 넣는 기준 데이터(시드가 아닌 데이터)가 생기면 이 방식은 그것까지 지운다. 그때 비우는 범위를 다시 정한다. 통합 테스트의 테이블 비우기도 같다.
- 초기화 중에 다른 요청이 행을 잠그고 있으면 `TRUNCATE`가 기다린다. E2E는 테스트를 하나씩 돌리고 테스트 사이에 부르므로 문제 되지 않는다.
