# 0100. 동시성 잠금 순서(개정): 사용자 행 → 선점 행 → 좌석 id 오름차순. 결제도 사용자 행을 먼저 잠그고, 해제는 사용자 행을 잠그지 않는다

- 상태: 에이전트 결정
- 날짜: 2026-11-27
- 결정한 사람: 에이전트(Issue #46이 결제의 잠금 순서, 교착 상태가 생기지 않는 근거, 해제의 사용자 행 잠금 여부를 에이전트에게 맡김. spec 2.4의 결과와 `backend/CLAUDE.md`의 'DB로 보장'을 지킨다)
- 관련: Issue [#46](https://github.com/Rasit-NP/curtain-call/issues/46), 대체하는 결정 [0073](0073-hold-concurrency.md), 결정 [0006](0006-idempotency-record.md), [0009](0009-seat-hold-id.md), [0070](0070-hold-schema.md), [0071](0071-missing-token-user-not-handled.md), [0074](0074-valid-hold-single-place.md), spec 2.2, 2.3, 2.4, 6.4, 6.6, 6.7

## 결정

0073을 대체한다. 선점 생성은 0073과 같고, 바뀐 것은 결제와 해제의 잠금이다.
0073은 "사용자 행 잠금은 같은 사용자의 해제·결제와는 한 줄로 세우지 않아도 4석을 넘기지 않는다"고 했지만, 결제에는 틀렸다(아래 '근거').

잠금 순서는 하나다: **사용자 행 → 선점 행 → 좌석(`id` 오름차순)**. 요청마다 필요한 잠금만 이 순서로 건다. 행 잠금은 모두 `FOR NO KEY UPDATE`다.

| 요청 | 잠금 순서 | 현재 시각을 읽는 때 |
|---|---|---|
| 선점 생성(6.4) | 요청한 사용자 행 → 좌석 | 사용자 행을 잠근 뒤. 보유 좌석 수, 좌석 판정, 만료 시각에 같은 값을 쓴다 |
| 결제(6.7) | 요청한 사용자 행 → (같은 키의 멱등 기록) → 선점 행 → 좌석 | 좌석을 잠근 뒤. 만료 판정(R4)에 쓴다 |
| 해제(6.6) | 선점 행 → 좌석 | 쓰지 않는다(만료된 선점도 해제한다) |

선점 생성(0073과 같다). `HoldService.create`는 한 트랜잭션(READ COMMITTED)에서:

1. `SELECT id FROM users WHERE id = ? FOR NO KEY UPDATE`: 같은 사용자의 선점 생성·결제를 한 줄로 세운다(R2).
2. 공연 조회, 좌석 id를 배열 매개변수 하나로 넘겨 모두 그 공연의 좌석인지 개수로 확인한다(404). 좌석 엔티티를 읽지 않는다.
3. 현재 시각을 한 번 읽고 보유 좌석 수로 한도를 검사한다(409 HOLD_LIMIT_EXCEEDED). 5단계에서 예매 좌석도 센다(spec 2.2).
4. 좌석을 `order by id for no key update` 한 문장으로 잠그고, 잠근 뒤 읽은 값과 좌석을 잡은 선점으로 판정한다(409 SEAT_ALREADY_HELD).
5. 선점을 저장하고 좌석을 HELD·holdId로 바꾼다.

결제(5단계):

- 사용자 행은 요청한 사용자(토큰의 `sub`)의 행이다. 선점의 주인을 먼저 읽지 않는다. 다른 사용자의 선점이면 404로 끝나 누구의 보유 좌석 수도 바꾸지 않으므로(요청한 사용자의 멱등 기록만 저장한다, spec 6.7.1) 주인의 행은 잠그지 않는다.
- 사용자 행을 트랜잭션의 첫 잠금으로 건다. 멱등 키 처리(spec 6.7 오류 표 3번)와 선점 확인(4번)보다 먼저다.
- 만료 판정(R4)의 현재 시각은 좌석까지 잠근 뒤에 읽는다.

해제(4단계): 사용자 행을 잠그지 않는다. 선점 행을 잠근 뒤 좌석을 `id` 오름차순으로 잠그고, 잠근 뒤 holdId가 이 선점인 좌석만 되돌린다(spec 2.3, 6.6).

## 근거

### 결제가 사용자 행을 잠가야 하는 이유(R2)

보유 좌석 수(spec 2.2)를 늘리는 요청은 선점 생성뿐이다. 결제는 유효한 선점을 예매로 바꾸고, 해제는 줄인다.
그런데 결제는 선점 생성이 세지 않는 것을 세는 것으로 바꿀 수 있다. 판정을 통과한 결제는 만료 시각을 넘겨 커밋될 수 있기 때문이다(spec 2.4의 R4).

1. 사용자 U가 2석 선점 H를 만료 1초 전에 결제한다. 결제는 좌석을 잠그고 만료 판정을 통과한 뒤, 모의 결제가 늦게 끝난다.
2. 만료 시각이 지난 뒤 U가 같은 공연의 다른 4석을 선점한다. 결제가 사용자 행을 잠그지 않으면 이 요청은 기다리지 않는다.
3. 이 요청이 보기에 H는 만료라 세지 않고, 결제가 만든 예매는 커밋 전이라 보이지 않는다(READ COMMITTED). 0 + 4석으로 한도를 통과한다.
4. 결제가 커밋되면 예매 2석 + 유효한 선점 4석 = 6석이다.

5단계에서 선점 생성이 선점 좌석과 예매 좌석을 두 문장으로 읽으면, 두 문장 사이에 결제가 커밋될 때 같은 좌석을 양쪽에서 모두 빼고 셀 수도 있다
(예매를 먼저 읽으면 아직 없고, 선점을 나중에 읽으면 이미 PAID라 세지 않는다).

결제와 선점 생성이 같은 사용자 행에서 한 줄로 서면 두 경우 모두 막힌다.

- 선점 생성이 먼저면: 결제는 선점 생성이 커밋한 뒤에 사용자 행을 얻고, 그 뒤에 현재 시각을 읽는다. 그래서 결제의 현재 시각 ≥ 선점 생성의 현재 시각이다.
  선점 생성이 H를 만료로 보고 세지 않았으면 결제도 H를 만료로 보고 409 HOLD_EXPIRED로 끝난다. H를 유효로 보고 셌으면 결제는 그 좌석을 예매로 바꿀 뿐이다.
- 결제가 먼저면: 선점 생성은 결제가 끝난 뒤에 보유 좌석 수를 세므로, 승인됐으면 예매를, 거절됐으면 그대로인 선점을 읽는다. 두 문장으로 읽어도 그 사이에 결제가 커밋되지 않는다.
- 시계는 거꾸로 가지 않는다고 본다(주입한 `Clock`).

결제가 만료 판정 뒤에 사용자 행을 잠그면 첫 경우가 깨진다. 결제가 만료 전 시각으로 판정한 뒤 사용자 행을 기다리는 사이, 선점 생성이 H를 만료로 보고 4석을 잡을 수 있다.
그래서 사용자 행은 맨 앞에 잠그고, 현재 시각은 모든 잠금 뒤에 읽는다.

### 해제는 사용자 행을 잠그지 않는다

- 해제는 보유 좌석 수를 줄이기만 한다. 결제처럼 세지 않던 것을 세게 만들지 않는다.
- 선점 생성이 보유 좌석 수를 세는 동안 해제가 커밋돼도, 선점은 한 문장으로 읽으므로 해제 전이나 해제 뒤 중 하나를 본다. 예매는 해제가 바꾸지 않으므로,
  5단계에서 선점과 예매를 두 문장으로 읽어도 결과는 해제 전이나 해제 뒤 중 하나와 같다.
- 해제 전을 보면 한도 판정이 409 쪽으로 틀릴 수 있지만, 선점 생성이 해제보다 먼저 처리된 것과 같은 결과다. 사용자 행으로 한 줄로 세워도 어느 쪽이 먼저인지는
  도착 순서에 달려 결과의 종류는 달라지지 않고, 해제가 선점 생성을 기다리게 할 뿐이다.

### 교착 상태가 생기지 않는 이유

- 모든 요청이 하나의 순서로만 잠근다. 사용자 행은 요청한 사용자의 행 하나, 선점 행은 요청의 선점 하나이고, 좌석은 `id` 오름차순이다.
  잠금을 기다리는 요청은 그 잠금보다 앞 순서의 잠금만 쥐고 있다. 기다림을 따라가면 순서가 계속 뒤로만 가므로 처음 요청으로 돌아오는 원이 생기지 않는다.
- 요청 쌍으로 보면:

  | 두 요청 | 겹칠 수 있는 잠금 | 결과 |
  |---|---|---|
  | 선점 생성 ↔ 선점 생성 | 같은 사용자면 사용자 행, 다른 사용자면 좌석 | 사용자 행에서 한 줄로 서거나, 좌석을 같은 순서로 잠근다 |
  | 선점 생성 ↔ 결제 | 같은 사용자면 사용자 행, 다른 사용자면 좌석(만료된 선점의 좌석) | 사용자 행에서 한 줄로 서거나, 좌석을 같은 순서로 잠근다 |
  | 선점 생성 ↔ 해제 | 좌석(만료 뒤 덮어쓴 좌석) | 좌석을 같은 순서로 잠근다 |
  | 결제 ↔ 결제, 결제 ↔ 해제, 해제 ↔ 해제 | 같은 선점이면 선점 행, 다른 선점이면 좌석 | 선점 행에서 한 줄로 서거나(spec 2.4), 좌석을 같은 순서로 잠근다 |

- `FOR NO KEY UPDATE`만 쓰므로 외래 키 확인이 거는 `FOR KEY SHARE`(선점·예매 같은 행을 저장할 때 그 행이 참조하는 사용자·공연·선점·좌석 행에 건다)와 부딪히지 않는다.
  그래서 기다림은 위 순서의 잠금끼리만 생긴다. 사용자 행을 지우거나 키를 바꾸는 기능은 없다.
- 같은 키 결제의 기다림(R5, [0006](0006-idempotency-record.md)): 같은 사용자의 결제는 사용자 행에서 이미 한 줄로 서므로, 멱등 기록(유니크 제약)에서 서로 기다리는 일이 없다.
  다른 사용자끼리는 키가 겹치지 않는다(사용자별 복합 유니크). 순서로는 사용자 행 뒤, 선점 행 앞이다.

### 사용자 행을 맨 앞에 두는 이유

선점 행 → 사용자 행 → 좌석으로 잠가도 원은 생기지 않는다(선점 생성은 사용자 행 → 좌석, 해제는 선점 행 → 좌석이라 하나의 순서를 이룬다). 그래도 사용자 행을 맨 앞에 둔다.

- 선점 생성과 같은 규칙이다: 사용자 행을 잠그는 요청은 그것을 가장 먼저 잠근다.
- 사용자 행을 기다리는 동안 다른 잠금을 쥐지 않는다. 선점 행을 먼저 잡으면 같은 선점의 해제가 같은 사용자의 선점 생성이 끝날 때까지 기다린다.
- spec 6.7의 검사 순서(3번 멱등 키 → 4번 선점)와 맞는다. 같은 사용자의 결제가 멱등 키를 확인하기 전에 이미 한 줄로 선다.

사용자 행을 좌석 뒤에 잠그면(선점 행 → 좌석 → 사용자 행) 교착 상태가 생긴다. 결제가 만료 직전 선점의 좌석을 잡고 사용자 행을 기다리는 동안,
같은 사용자의 선점 생성이 사용자 행을 잡고 그 좌석(만료로 보임)을 기다릴 수 있다.

## 고려했지만 고르지 않은 것

- 해제도 사용자 행 잠금: 순서를 지키면 교착 상태는 생기지 않지만, 위 이유로 필요 없고 기다림만 는다. 4단계에서 필요해지면 사용자 행을 맨 앞에 잠그면 된다.
- 결제를 마칠 때 보유 좌석 수를 다시 검사해 넘으면 거부: 판정을 통과한 결제는 마친다는 spec 2.4(R4)와 어긋나고, 결제 응답이 바뀐다(정책 결정).
- 결제 중인 선점을 따로 저장해(예: 상태 `PAYING`) 선점 생성이 세게 함: 모의 결제 전에 따로 커밋해야 하고, 결제가 500으로 끝나거나 서버가 멈추면 그 상태를 되돌릴 방법이 필요하다.
- SERIALIZABLE 격리 수준: 충돌을 직렬화 실패로 끊으므로 다시 시도하는 코드가 필요하다. 다시 시도하지 않으면 500이다.
- 공연 행 잠금, 사용자 id로 PostgreSQL advisory lock, JVM 안의 락: 0073과 같은 이유로 고르지 않았다.

## 적용과 남은 점

- 지금 코드(선점 생성, #41)는 바꿀 것이 없다. 0073의 구현이 이 결정의 선점 생성이고, 0073 '적용과 남은 점'의 되돌림 확인 기록(정렬만 빼서는 교착 상태 테스트가 실패하지 않음)도 그대로다.
- 해제(4단계): 위 순서대로 사용자 행 없이 선점 행 → 좌석으로 잠근다.
- 결제(5단계): 위 순서대로 구현한다. `docs/test-matrix.md` R2의 5단계 동시성 행(모의 결제를 래치로 멈춤)으로 재현·검증한다.
  되돌림 확인은 결제의 사용자 행 잠금을 빼는 것으로 한다. 그 테스트가 실패해야 한다.
- 결제가 모의 결제를 기다리는 동안 같은 사용자의 선점 생성(다른 공연 포함)과 다른 결제도 기다린다. 테스트가 아닌 프로필에서는 모의 결제가 바로 끝나므로 문제가 되지 않는다.
  실제 PG 연동은 범위 밖이다.
- 토큰의 사용자 행이 없으면([0071](0071-missing-token-user-not-handled.md)) 잠글 행이 없어 한 줄로 서지 않는다. 그런 사용자에게는 선점·예매가 없으므로 보유 좌석 수는 늘 0이다.
- 코드와 결정을 읽고 정했다. 결제 코드가 없어 재현하지 않았다.
