# 0143. 결제 동시성 테스트: 모의 결제를 멈추고, 나중 요청이 DB 행 잠금을 기다리는 것을 pg_stat_activity로 확인한 뒤 푼다

- 상태: 에이전트 결정
- 날짜: 2026-11-28
- 결정한 사람: 에이전트(Issue #55 '에이전트가 정하는 것': 테스트 방법)
- 관련: Issue [#55](https://github.com/Rasit-NP/curtain-call/issues/55), 결정 [0100](0100-hold-concurrency-v2.md), [0121](0121-release-race-test-staggered.md), [0142](0142-payment-impl.md), spec 2.4, 6.7.2

## 결정

`PaymentConcurrencyTest`의 순서가 정해진 경합(R2 결제와 선점, R4 결제 중 다른 사용자의 선점, R4 잠금을 기다리는 동안 만료, 같은 선점의 다른 키 결제, 결제와 해제)은:

1. 모의 결제의 `pauseNext()`를 지정하고 결제를 보낸다. `Pause.awaitEntered`로 결제가 판정을 통과해 모의 결제에서 멈춘 것을 확인한다(잠금을 쥐고 있다).
2. 필요하면 시계를 옮기고(예: 만료 시각) 나중 요청을 보낸다.
3. `DatabaseLocks.awaitLockWaitersOrDone`으로 PostgreSQL의 `pg_stat_activity`에서 `wait_event_type = 'Lock'`인 연결이 생기거나 나중 요청이 끝날 때까지 기다린다.
4. 결제를 풀고, 두 응답과 DB 최종 상태를 본다. 마지막에 나중 요청이 '잠금을 기다렸는지'도 단언한다.

교착 상태 테스트(결제와 다른 사용자의 같은 좌석 선점)는 순서를 정하지 않고 `CountDownLatch`로 함께 출발시키며, 반복마다 결제를 0~10ms(`(반복 번호 % 6) × 2`) 늦게 보낸다(결정 0121과 같은 방법). 50회 반복한다.

## 근거

- 결정 0121의 교훈: 같은 순간에 출발시켜도 잠그기 전 단계의 길이 차이로 한 순서만 나올 수 있다. 결제에는 모의 결제라는 원래 있는 멈출 지점이 있어(결정 0121 '고려했지만 고르지 않은 것'),
  "결제가 잠금을 쥔 채 판정을 통과한 뒤"라는 순서를 시간에 기대지 않고 매번 만든다.
- 나중 요청이 잠금을 기다리는지 sleep으로 짐작하지 않고 DB에 묻는다. 기다리기 시작한 뒤에 풀어야 '나중 요청이 결제가 커밋한 값을 읽는다'는 순서가 확실하다.
  구현의 잠금을 되돌리면 나중 요청은 기다리지 않고 먼저 끝나므로, 기다림과 끝남 중 먼저 일어난 쪽에서 멈춰 테스트가 오래 걸리지 않는다.
- 결과 단언을 '기다렸는지' 단언보다 먼저 둔다. 되돌렸을 때 실패 메시지가 결과의 차이(예: 409 대신 201)를 먼저 보여 준다. 실패 메시지에 관찰한 상태(`WAITING_FOR_LOCK`·`FINISHED`)를 넣었다.
- 교착 상태는 두 요청이 좌석을 잠그는 단계에서 겹쳐야 생긴다. 결제는 좌석을 잠그기 전 단계(사용자 행, 선점 행)가 선점 생성보다 짧아 0~10ms 늦춰 겹치게 했다.
  되돌림 확인: 결제가 좌석을 id 내림차순으로 하나씩 잠그게 바꾸자 4회 실행 모두 6번째 반복(지연 0ms)에서 500이 났다.
  로그를 확인한 4번째 실행에서 원인은 PostgreSQL `deadlock detected`(`CannotAcquireLockException`)였다.

## 고려했지만 고르지 않은 것

- 나중 요청을 보낸 뒤 고정 시간(sleep)을 기다렸다가 결제를 풂: 기계가 느리면 나중 요청이 아직 잠금에 닿지 않아, 테스트가 의도한 순서를 만들지 못한 채 통과할 수 있다.
- `pg_locks`에서 잠금 종류까지 확인: 테스트가 잠금 구현(행 잠금 모드)에 묶인다. 기다리는 연결이 있는지만 본다. 테스트 DB 컨테이너는 이 테스트만 쓰므로 다른 연결이 섞이지 않는다.
- 결제와 선점 생성 사이에 서비스 대기 지점을 더함: 운영 코드에 테스트 전용 지점이 생긴다(결정 0121과 같은 이유).

## 적용과 남은 점

- 코드: `backend/src/test/java/com/curtaincall/payment/PaymentConcurrencyTest.java`, `support/DatabaseLocks.java`, `payment/infra/FakePaymentGateway.java`의 `Pause`.
- 원래 코드로 `PaymentConcurrencyTest`와 `HoldConcurrencyTest`를 3회 연속 실행해 모두 통과했다.
- 교착 상태 테스트의 지연 값은 이 환경(로컬 Docker의 PostgreSQL 17, MockMvc)에서 정했다(결정 0121 '적용과 남은 점'과 같다).
