# 0073. 선점 동시성: 사용자 행 잠금으로 같은 사용자 요청을 한 줄로 세우고, 좌석은 id 오름차순 한 문장으로 잠그며, 404·한도 검사는 좌석을 잠그기 전에

- 상태: 대체됨(→0100)
- 날짜: 2026-11-27
- 결정한 사람: 에이전트(Issue #41이 동시성 구현 방법을 에이전트에게 맡김. spec 2.4의 결과와 `backend/CLAUDE.md`의 'DB로 보장'을 지킨다)
- 관련: Issue [#41](https://github.com/Rasit-NP/curtain-call/issues/41), 결정 [0003](0003-hold-is-seat-bundle.md), [0070](0070-hold-schema.md), [0071](0071-missing-token-user-not-handled.md), spec 2.4, 6.4

## 결정

`HoldService.create`는 한 트랜잭션(READ COMMITTED)에서 다음 순서로 처리한다.

1. `SELECT id FROM users WHERE id = ? FOR NO KEY UPDATE`: 같은 사용자의 선점 요청을 한 줄로 세운다(R2).
2. 공연 조회. 없으면 404.
3. `SELECT count(*) FROM seats WHERE performance_id = ? AND id = ANY(?)`: 좌석 id를 배열 매개변수 하나로 넘겨 모두 그 공연의 좌석인지 확인한다(404).
   좌석 엔티티를 읽지 않는다.
4. 현재 시각을 한 번 읽고, 같은 사용자·같은 공연의 ACTIVE 선점으로 보유 좌석 수를 세어 한도를 검사한다(409 HOLD_LIMIT_EXCEEDED).
5. `select ... from seats where performance_id = ? and id in (...) order by id for no key update`: 좌석을 id 오름차순으로 한 문장에 잠근다(R1).
   잠근 뒤 읽은 값과 좌석을 잡은 선점으로 선점할 수 있는지 판정한다(409 SEAT_ALREADY_HELD).
6. 선점을 저장하고 좌석을 HELD·holdId로 바꾼다.

## 근거

- R1: 좌석 행 잠금으로 같은 좌석을 두 요청이 동시에 판정하지 못하게 한다. 기다린 요청은 앞 요청이 커밋한 값(HELD, holdId)을 읽어 409가 된다.
  id 오름차순 잠금은 spec 2.4가 정했다.
- R2: 보유 좌석 수를 세고 선점을 저장하는 사이에 같은 사용자의 다른 요청이 끼면 둘 다 한도를 통과한다. 사용자 행을 잠가 한 줄로 세운다(spec 2.4의 예).
- `FOR NO KEY UPDATE`: `FOR UPDATE`는 외래 키 확인이 거는 `FOR KEY SHARE`와 부딪힌다. 결제(5단계)가 같은 사용자의 예매 행을 저장할 때
  선점 요청과 서로 기다리는 일을 피한다. 좌석 잠금도 Hibernate 7의 `PESSIMISTIC_WRITE`가 PostgreSQL에서 `for no key update`로 나간다(SQL 로그로 확인).
- 404와 한도 검사를 좌석 잠금보다 먼저: 오류 순서(404 → 한도 → 좌석)를 지키면서, 한도를 넘는 요청은 좌석을 잠그지 않는다. 그래서 잠그는 좌석은 4석 이하다.
  개수 확인은 엔티티를 읽지 않으므로 `backend/CLAUDE.md`의 '잠금 조회 전에 같은 엔티티를 일반 조회로 불러오지 않는다'를 지킨다.
- 배열 매개변수: 5석 이상은 400이 아니라 409(spec 6.4)라 요청의 좌석 id 개수에 상한이 없다. `IN (:ids)`는 id마다 매개변수를 하나씩 만들어,
  PostgreSQL JDBC 드라이버의 상한(65,535개)을 넘으면 500이 됐다(7만 개 테스트로 찾음).
- 현재 시각을 한 번 읽어 보유 좌석 수, 좌석 판정, 만료 시각에 같은 값을 쓴다. 잠금을 기다린 동안 지난 시간만큼 판정이 보수적이 될 뿐(409 쪽) 두 선점이 한 좌석을 잡지는 않는다.

## 고려했지만 고르지 않은 것

- 조건부 UPDATE(`UPDATE seats ... WHERE id IN (...) AND (AVAILABLE이거나 만료된 선점)`)와 영향받은 행 수: 만료 판정을 SQL에 다시 써야 하고
  (유효 판정이 두 곳, [0074](0074-valid-hold-single-place.md)), 한도 검사가 좌석 검사보다 먼저라 사용자 직렬화는 따로 필요하다.
- 좌석을 한 좌석씩 잠금: 요청 순서대로 잠그면 교착 상태가 된다(되돌림 확인에서 500). 정렬해서 잠그면 되지만 문장이 좌석 수만큼 는다.
- 공연 행을 잠가 직렬화: 다른 사용자가 서로 다른 좌석을 선점하는 요청까지 한 줄로 선다.
- 사용자 id로 PostgreSQL advisory lock: 사용자 행이 없어도 되지만 잠금 키를 따로 관리해야 한다. 사용자 행이 없는 경우는 따로 처리하지 않기로 했다(0071).
- JVM 안의 락: `backend/CLAUDE.md`가 금지한다(서버가 여러 대면 깨진다).

## 적용과 남은 점

- 되돌림 확인에서 `order by id`만 빼서는 테스트가 실패하지 않았다. 한 문장으로 잠그면 두 요청이 같은 실행 계획(인덱스의 정렬된 키, 또는 같은 물리 순서)으로
  같은 순서로 잠그기 때문이다. 실행 계획이 다른 경우까지 막으려고 spec 2.4대로 정렬을 둔다. 교착 상태 테스트는 요청 순서대로 한 좌석씩 잠그는 구현을
  잡는다(그렇게 바꾸면 PostgreSQL이 교착 상태를 끊어 500으로 실패).
- 결제·해제(4·5단계)는 spec 2.4대로 선점 행을 먼저 잠그고 좌석을 id 오름차순으로 잠근다. 선점 생성은 사용자 행 → 좌석 순이므로, 좌석을 같은 순서로
  잠그는 한 서로 교착 상태가 되지 않는다.
- 사용자 행 잠금은 같은 사용자의 해제·결제와는 한 줄로 세우지 않는다. 해제는 보유 좌석 수를 줄이기만 하고 결제는 선점을 예매로 바꿀 뿐이라,
  한도 판정이 보수적으로(409 쪽으로) 틀릴 수는 있어도 4석을 넘기지는 않는다.
