# 0151. 멱등 키 처리: 사용자 행 뒤에 INSERT … ON CONFLICT DO NOTHING으로 키를 먼저 잡고, 결과 응답을 같은 트랜잭션에서 채운다. 응답 모양은 API 계층이 넘기고, 처음 응답도 저장값으로 만든다

- 상태: 에이전트 결정
- 날짜: 2026-11-28
- 결정한 사람: 에이전트(Issue #56 '에이전트가 정하는 것': 같은 키의 기록을 찾고 저장하는 방법, 클래스 구조. 명세 2.4·6.7.1과 결정 0100의 결과를 지키고 DB로 보장한다)
- 관련: Issue [#56](https://github.com/Rasit-NP/curtain-call/issues/56), 결정 [0006](0006-idempotency-record.md), [0012](0012-backend-error-mapping.md),
  [0071](0071-missing-token-user-not-handled.md), [0100](0100-hold-concurrency-v2.md), [0142](0142-payment-impl.md), [0150](0150-idempotency-record-schema.md), spec 2.4, 6.7, 6.7.1

## 결정

결제(`PaymentService.pay`, 한 트랜잭션, READ COMMITTED)는 결정 0142의 흐름에서 비워 둔 2번을 채운다.

1. 요청한 사용자 행을 잠근다(그대로).
2. **같은 사용자·같은 키의 멱등 기록을 잡는다.** `INSERT INTO idempotency_records (user_id, idempotency_key, hold_id, created_at) … ON CONFLICT (user_id, idempotency_key) DO NOTHING`
   (`IdempotencyRecordRepository.claim`)으로 응답이 빈 기록을 넣고, 같은 키의 기록을 읽는다.
   - 넣었으면(1행) 이 요청이 키를 처음 쓴 것이다. 3번으로 간다.
   - 넣지 못했으면(0행) 커밋된 기록이 있다. `holdId`가 같으면 저장한 응답을 그대로 돌려주고 끝낸다(모의 결제를 부르지 않는다). 다르면 `400 INVALID_INPUT`(`ApiException`)이고,
     바꾼 것이 없으므로 되돌려도 같다.
3. 선점 행 → 좌석 → 현재 시각 → 판정 → 모의 결제(결정 0142의 3~7번 그대로, `process`).
4. 결과(`PaymentOutcome`)를 저장할 응답(`StoredResponse`: 상태 코드와 본문)으로 바꿔 2번의 기록에 채운다(UPDATE). 결제·예매와 함께 커밋된다.

응답의 모양과 클래스 구조:

- 결과를 응답으로 바꾸는 방법은 API 계층(`payment.api.StoredPaymentResponses`)이 정하고, 컨트롤러가 함수(`toResponse`)로 서비스에 넘긴다. 서비스는 그 함수를
  트랜잭션 안에서 불러 저장하고, 저장한 응답을 돌려준다. 서비스는 API DTO(`PaymentResponse`)를 모른다.
- 컨트롤러는 처음 요청이든 같은 키로 다시 보낸 요청이든 서비스가 돌려준 저장한 응답으로 응답한다(`StoredPaymentResponses.respond`). 201은 저장한 JSON을 읽어 돌려주고,
  402·404·409는 저장한 code·detail로 `ApiException`을 던져 공통 처리기가 오류 본문을 만든다(결정 0150).
- 기록의 생성 시각은 2번에서 주입한 `Clock`으로 읽는다. 판정에 쓰지 않는다(만료 판정의 시각은 결정 0100대로 모든 잠금 뒤에 따로 읽는다).

## 근거

- **키를 먼저 잡는 것(2번에서 INSERT)**: 명세 2.4의 결제 잠금 순서 "사용자 행 → 같은 키의 멱등 기록 → 선점 행 → 좌석"을 그대로 만든다. 같은 (사용자, 키)를 다른 트랜잭션이
  넣고 커밋하지 않았으면 이 INSERT는 유니크 제약에서 그 트랜잭션이 끝날 때까지 기다리고, 커밋되면 0행, 되돌려지면(500) 1행이다. 그래서 "같은 키 요청은 먼저 요청이 끝날 때까지
  기다렸다가 그 결과를 받고, 먼저 요청이 500이었으면 처음 온 요청처럼 처리한다"(spec 6.7.1)를 유니크 제약(`backend/CLAUDE.md`: R5는 DB 유니크 제약으로 보장)이 직접 지킨다.
- 같은 사용자의 결제는 사용자 행에서 이미 한 줄로 서므로(결정 0100 '같은 키 결제의 기다림'), 지금은 2번의 INSERT가 실제로 기다리는 일이 없다. 그래도 키를 먼저 잡아 두면
  사용자 행 잠금이 빠지거나 바뀌어도 R5가 깨지지 않는다. 되돌림 확인: 사용자 행 잠금만 빼면 R5 테스트가 모두 통과했고(INSERT가 기다림),
  사용자 행 잠금을 빼고 기록을 처리 끝에 저장하게 바꾸면 같은 키 동시 요청 5개가 `[201, 500, 500, 500, 500]`이 됐다(나중 요청들은 먼저 요청이 커밋하기 전에 기록을 확인해 없다고 보고,
  선점 행을 기다린 뒤 404로 처리됐다. 끝에 넣으려던 기록은 유니크 제약 때문에 이미 있는 먼저 요청의 기록이어서 응답을 채우지 못하고 500).
- **교착 상태가 없는 이유**: 멱등 기록에서 기다리는 것은 같은 (사용자, 키)끼리뿐이고, 그 요청들은 사용자 행 잠금을 먼저 잡는다. 결정 0100의 '하나의 순서'에 기록이 사용자 행과 선점 행 사이로 들어갈 뿐이다.
  기록 INSERT가 사용자 행에 거는 외래 키 확인(`FOR KEY SHARE`)은 같은 트랜잭션이 쥔 `FOR NO KEY UPDATE`와도, 다른 트랜잭션의 것과도 부딪히지 않는다.
- **결과를 같은 트랜잭션에서 저장하는 것**: 결제·예매와 기록이 함께 커밋되거나 함께 되돌려진다. 결제는 됐는데 기록이 없는 상태(같은 키로 다시 보내면 404)나, 500인데 기록이 남은 상태가 생기지 않는다.
- **응답 모양을 함수로 넘기는 것**: 저장은 커밋 전, 서비스의 트랜잭션 안에서 해야 한다. 그런데 응답 본문(`PaymentResponse`)은 API 계층의 DTO다. 서비스가 API DTO를 직접 쓰면 계층이 거꾸로 되고,
  컨트롤러가 트랜잭션을 열면 트랜잭션 경계가 컨트롤러로 올라간다. 함수로 넘기면 호출하는 곳(컨트롤러)에서 무엇을 저장하는지 보인다.
- **처음 응답도 저장값으로 만드는 것**: 처음 응답과 다시 보낸 응답이 같은 값에서 같은 코드로 만들어지므로 '그대로'가 구조로 보장된다. 처음에만 쓰는 경로가 따로 있으면 두 경로의 결과가 같은지 따로 맞춰야 한다.
- **토큰의 사용자가 DB에 없으면 500**: 2번의 INSERT를 외래 키가 막는다. 결정 0071(사람이 정함: 따로 처리하지 않고 외래 키가 막아 500, "결제(5단계)도 … 이 결정을 따른다")대로다.

## 고려했지만 고르지 않은 것

- 기록을 먼저 확인만 하고(SELECT) 처리 끝에 INSERT: 사용자 행 잠금이 있는 동안은 결과가 같지만, 유니크 제약이 기다림을 만들지 못하고 마지막 방어로만 남는다(위 되돌림 확인에서 500).
  명세 2.4의 잠금 순서와도 다르다(기록이 좌석 뒤).
- 기록을 `SELECT … FOR UPDATE`로 잠금: 키를 처음 쓰는 요청에는 잠글 행이 없다.
- 처리 중 상태를 따로 커밋하고 같은 키의 나중 요청에 409: 결정 0006이 고르지 않았다(새 오류 코드, R5의 같은 결과와 어긋남).
- 사용자 id·키로 PostgreSQL advisory lock: 결정 0100과 같은 이유(유니크 제약으로 충분하고, 잠금이 DB 행과 따로 논다).
- 서비스가 `PaymentResponse`를 직접 만들어 저장: 위 '근거'(계층이 거꾸로 된다).
- 서블릿 필터나 인터셉터가 HTTP 응답을 저장: 결제와 다른 트랜잭션에서 저장하게 되어, 결제는 커밋됐는데 기록 저장 전에 서버가 멈추면 같은 키 재요청이 404가 된다.
- 같은 키·다른 선점의 400을 결과 값으로 돌려 커밋: 바꾼 것이 없어 예외로 되돌려도 같고, 저장하지 않는 응답이므로 저장하는 결과 값(`PaymentOutcome`)과 섞지 않는다.

## 적용과 남은 점

- 코드: `PaymentService.pay`·`process`, `IdempotencyRecord`(`isFor`, `response`, `complete`), `IdempotencyRecordRepository.claim`, `StoredPaymentResponses`, `PaymentController`.
- 결정 0142의 흐름 2번("#56 자리")을 이 결정이 채운다. 0142의 다른 내용은 그대로다. 0142 '적용과 남은 점'의 "토큰의 사용자 행이 없으면 404"는 이제 500이다(결정 0150 '적용과 남은 점').
- 같은 키의 나중 요청은 먼저 요청이 모의 결제를 기다리는 동안 함께 기다린다. 테스트가 아닌 프로필에서는 모의 결제가 바로 끝난다(결정 0100 '적용과 남은 점'과 같다).
- 사용자 행 잠금이 있는 한, 2번의 위치(선점 행 앞인지 뒤인지)는 동시성 테스트로 구별되지 않는다(위 되돌림 확인). 사용자 행 잠금을 바꿀 때는 이 결정을 함께 본다.
