# 0204. 살아남은 변이는 다섯 갈래로 나누고 설정으로 빼지 않는다. 스프링 시작 코드는 손으로 변이를 넣어 통합 테스트로 확인하고, 직접 만들 수 있으면 단위 테스트를 더한다

- 상태: 에이전트 결정
- 날짜: 2026-11-28
- 결정한 사람: 에이전트(Issue #69 '에이전트가 정하는 것': 살아남은 변이를 나누는 기준, 동등 변이를 설정으로 뺄지)
- 관련: Issue [#69](https://github.com/Rasit-NP/curtain-call/issues/69), 결정 [0200](0200-pit-setup.md), [0201](0201-pit-target-classes.md), [0203](0203-pit-threshold.md)

## 결정

살아남은 변이와 덮이지 않은 변이를 하나씩 바이트코드(`javap`)와 테스트에 대조해 다음 중 하나로 나눈다. 결과는 `docs/mutation-testing.md`에 변이마다 적는다.

| 갈래 | 기준 | 하는 일 |
|---|---|---|
| 테스트 빈틈 | 변이가 바깥 동작이나 문서로 정한 계약(명세, 결정 기록, 메서드 설명의 예외)을 바꾸는데 잡는 테스트가 없다 | 그 변이를 죽이는 테스트를 더하고, 재측정에서 그 테스트가 죽인 것을 확인한다 |
| 동등 변이 | 도달할 수 있는 모든 상태에서 결과가 같다. 클래스 불변식이나 DB 제약이 막는 상태에서만 달라지는 것도 여기 넣는다 | 근거(불변식·제약)를 적는다 |
| 죽은 코드 | 정상 흐름에서 도달할 수 없거나 부르는 곳이 없다 | 근거를 적는다. 운영 코드를 지우는 것은 이 Issue의 범위 밖이다 |
| 검증할 가치가 낮음 | 바뀌는 것이 계약이 아니다(예: 명세가 '바뀔 수 있다'고 한 `detail` 문구) | 근거를 적는다 |
| PIT 측정 한계 | 스프링이 시작할 때만 도는 코드(빈 생성, 보안 설정 DSL)라 PIT가 그 동작을 확인하는 테스트를 돌리지 못한다 | 손으로 같은 변이를 넣어 통합 테스트가 잡는지 확인한다. 빈 생성 메서드를 스프링 없이 직접 부를 수 있으면 단위 테스트를 더한다 |

- 어느 갈래도 설정(`excludedMethods`, `excludedClasses`, `avoidCallsTo`)으로 빼지 않는다. 대상 클래스 안의 변이는 모두 점수에 넣는다.
- 살아남은 변이가 운영 코드 결함을 드러내면 실패하는 테스트를 먼저 쓰고 고친다. 고치면 바깥 동작이 바뀌는 경우는 고치기 전에 사람에게 묻는다(Issue #69 '이미 정한 정책').

## 근거

- PIT의 '스프링 시작 코드' 한계를 확인했다. `SecurityConfig`·`JwtConfig`의 빈 생성 코드 변이 10개는 토큰 검증 테스트(`AuthenticationTest`)가 있는데도 살아남았다.
  모든 테스트 결과를 남기게(`fullMutationMatrix`) 잠시 바꿔 보니, 그 변이에 돈 테스트는 컨텍스트 5종을 처음 만든 테스트 5개뿐이었다.
  스프링 테스트 컨텍스트는 한 번 만들면 다시 쓰므로, 시작 코드의 줄은 컨텍스트를 처음 만든 테스트만 덮은 것으로 잡히고, 그 테스트는 토큰 검증을 확인하지 않는다.
  같은 10개를 손으로 넣고 인증 통합 테스트(`AuthenticationTest`, `E2eProfileAuthTest`, `TestDataReset*`, `LoginApiTest`)를 돌리자 10개 모두 실패했다. 테스트 빈틈이 아니다.
- `JwtConfig`의 빈 생성 메서드(`jwtEncoder`, `jwtDecoder`, `validator`)는 스프링 없이 부를 수 있어 단위 테스트를 더했다. 토큰 검증 규칙이 `verify.sh quick`(단위 테스트)에서도 확인되고,
  PIT도 이 6개를 잰다. `SecurityConfig`는 `HttpSecurity`가 스프링 컨텍스트 안에서만 만들어져 단위 테스트로 확인할 수 없어 '측정 한계'로 남긴다.
- 설정으로 빼지 않는 이유: 뺀 변이는 리포트에 보이지 않아, 나중에 그 코드가 바뀌어도 다시 볼 계기가 없다. 남긴 채 이유를 적으면 7단계 재측정에서 같은 목록과 비교할 수 있다.
  분류를 마친 변이 수가 정해져 있어 기준값(결정 0203)으로 퇴보를 잡을 수 있다.
- 동등 변이에 불변식·DB 제약이 막는 상태를 넣는 이유: 그 상태를 만들려면 리플렉션이나 DB 제약을 끄는 테스트가 필요하다. 그런 테스트는 실제로 일어날 수 없는 경우를 고정해 코드를 바꾸기 어렵게 만든다.

## 고려했지만 고르지 않은 것

- 스프링 시작 코드를 대상에서 빼기: 점수는 깔끔해지지만 R6의 경로 보호가 측정에서 사라진다. 재지 못한다는 것도 측정 결과로 남긴다.
- 상용 플러그인(Arcmutate Spring 플러그인): PIT가 실행 끝에 권했다. 유료이고, 손으로 넣은 변이 확인으로 같은 질문(테스트가 잡는가)에 답할 수 있다.
- 동등 변이를 죽이려고 리플렉션으로 불변식을 깨는 테스트: 위 근거.
- 쓰는 곳 없는 `Seat.getPerformance()`를 지우기: 운영 코드 변경이라 이 Issue의 범위('결함 수정 밖의 운영 코드 변경'은 범위 밖) 밖이다.

## 적용과 남은 점

- 손으로 넣은 변이 확인은 7단계 재측정에서도 같은 10개로 다시 한다(목록은 `docs/mutation-testing.md`).
- `SecurityConfig` 4개가 살아남는 한 이 클래스의 점수는 0%다. PIT로는 이 클래스의 퇴보를 잡지 못하므로, 경로 보호를 바꾸는 PR(3단계 회원가입의 공개 경로 등)은
  지금처럼 R6 통합 테스트와 규칙 코드 되돌림 확인(루트 `CLAUDE.md` '테스트 원칙')으로 지킨다.
