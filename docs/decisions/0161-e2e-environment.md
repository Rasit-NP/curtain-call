# 0161. E2E 환경: 실행마다 자기 전용 백엔드·프론트엔드·임시 DB를 빈 포트에 새로 띄우고 끝나면 내린다. 사람의 개발 환경은 쓰지도 건드리지도 않는다

- 상태: 채택
- 날짜: 2026-11-28
- 결정한 사람: 사람(Issue #59 '아직 정하지 않은 정책' 1번. 이 Issue 세션에서 선택지 셋을 묻고, 사람이 추천인 1번을 골랐다)
- 관련: Issue [#59](https://github.com/Rasit-NP/curtain-call/issues/59), 결정 [0011](0011-dev-db-credentials.md), [0013](0013-flyway-out-of-order-local.md),
  [0160](0160-e2e-reset-impl.md), [0162](0162-e2e-setup-impl.md)(구현)

## 결정

- E2E는 그 체크아웃의 코드로 백엔드(`e2e` 프로필), 프론트엔드 개발 서버, DB를 실행마다 새로 띄우고 끝나면 내린다. 이미 떠 있는 서버는 다시 쓰지 않는다.
- E2E DB는 실행마다 새로 만드는 임시 DB다(그 체크아웃의 마이그레이션과 시드만 들어간다). 개발 DB(compose `db`, 5432)와 8080·5173 서버는 쓰지도 건드리지도 않는다.
- 포트는 실행마다 빈 포트를 고른다. 워크트리 여러 곳에서 동시에 E2E를 돌려도 부딪히지 않는다.
- `e2e` 프로필에서 개발 DB 주소 기본값을 뺀다. `e2e` 프로필로 띄운 서버가 개발 DB에 붙어 초기화로 개발 데이터를 지우는 일이 생길 수 없게 한다.
- 프론트엔드 개발 서버의 프록시 대상은 기본값(`http://localhost:8080`)을 그대로 두고, E2E만 환경변수로 바꾼다. 사람의 `npm run dev`는 그대로다.
- `compose.yaml`에 `name: curtain-call`을 넣어 개발 DB는 어느 체크아웃에서 띄워도 하나다. 메인 체크아웃의 프로젝트 이름과 같아서 사람이 쓰던 컨테이너와 데이터는 그대로다.

## 근거

물을 때 보인 이 기계의 상태와 근거다.

- 사람이 IntelliJ로 띄운 백엔드(`local`)가 8080에 있었다. E2E가 이 서버를 다시 쓰면 초기화 API가 없어 401로 실패하고, 메인 체크아웃의 코드를 시험하게 된다.
- `local`과 `e2e`가 같은 DB(5432)를 써서, E2E 초기화가 개발 데이터를 지운다.
- `compose.yaml`에 `name:`이 없어, 워크트리에서 `docker compose up -d db`를 하면 폴더 이름의 프로젝트로 DB를 하나 더 만들려다 5432에서 충돌했다.
- Issue별 세션을 동시에 돌리는 방식(결정 0027)에서 PR 전 전체 검증(이제 E2E 포함)이 서로 부딪히지 않아야 한다.

## 고려했지만 고르지 않은 것

- E2E 전용 고정 포트(물을 때 2번): 더 단순하지만 한 번에 하나의 E2E만 돈다. 다른 워크트리의 E2E가 돌고 있으면 시작할 때 포트가 겹쳐 실패한다.
- 지금 규칙(물을 때 3번, 8080·5173 재사용, `local`·`e2e`가 같은 DB): E2E 전에 사람이 서버를 끄고 초기화가 개발 데이터를 지우는 것을 받아들여야 하며, 여러 세션이 같은 DB를 초기화하며 섞인다.

## 적용과 남은 점

- 구현 방법(임시 DB를 띄우는 방법, 빈 포트를 고르는 방법)은 결정 [0162](0162-e2e-setup-impl.md)다.
- 대가: 실행마다 백엔드를 새로 띄우므로 기동 시간(수십 초)이 더 든다.
