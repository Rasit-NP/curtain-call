# 0044. 정책 결정은 구현 전에 사람에게 묻는다

- 상태: 채택
- 날짜: 2026-11-27
- 결정한 사람: 사람(2026-11-27 메인 세션 대화). 범위 문구는 2026-11-27 Issue #33 세션에서 사람이 초안을 보고 골랐다.
- 관련: Issue [#33](https://github.com/Rasit-NP/curtain-call/issues/33), 결정 [0045](0045-decision-status-by-decider.md), 결정 [0031](0031-security-paths-and-error-dispatch.md)~[0043](0043-frontend-auth-required-sent-token.md)

## 결정

정책 결정은 구현 전에 사람에게 묻고, 답을 받은 뒤 구현한다. 범위와 방법은 루트 `CLAUDE.md` '작업 흐름'의 '정책 결정'에 둔다.

- 정책(묻는다): 사용자가 보거나 겪는 동작, API 계약(경로, 요청·응답 형식, 상태 코드, `code` 매핑, 공개 경로), 계정·비밀번호·인증·보안, 명세나 Issue가 "Issue에서 정한다"고 맡긴 값, 비즈니스 규칙이 모호하거나 새 규칙이 필요하거나 규칙끼리 충돌할 때.
- 정책이 아닌 것(에이전트가 정한다): 바깥에서 보이는 동작을 바꾸지 않는 내부 구현. 예: 클래스·모듈 구조, 내부 이름, 테스트 방법, 라이브러리 설정.
- 판단이 애매하면 정책으로 본다. 리뷰 지적을 고치다 생긴 정책 결정도 묻는다.
- Issue 세션에서 직접 묻고 답을 기다린다. 선택지, 추천, 근거를 함께 쓰고, 구현 전에 보이는 것은 모아서 한 번에 묻는다. 메인 세션은 결과를 확인할 때 답을 기다리는 세션이 있으면 사람에게 알린다.
- Issue를 만들 때 이미 정한 정책과 아직 정하지 않은 정책을 나눠 적는다.
- 세션에서 답을 받으면 '사람에게 넘기는 조건'의 코멘트·라벨 없이 진행한다.

## 근거

- #27·#28(PR #32·#31)에서 세션들이 시드 계정, 공개 경로, `code` 매핑, 로그인 뒤 이동 같은 정책을 묻지 않고 정해 구현한 뒤 PR 본문에 링크만 걸었다(0031~0043). 사람은 이것이 제안이 아니라 통보라고 지적했다.
- 그때 규칙은 "규칙이 모호하면 사람에게 넘긴다"뿐이라 무엇이 정책인지를 세션이 판단했고, 세션들은 거의 모든 것을 '명세 안의 세부'로 봤다. 범위를 예와 함께 적어 그 판단을 세션에 맡기지 않는다.
- 애매하면 정책으로 보는 이유: 묻지 않고 정했다가 바꾸면 구현, 테스트, 문서를 다시 고쳐야 한다. 한 번 묻는 비용이 더 작다.
- 리뷰 수정을 넣은 이유: 0037~0039·0043은 사람이 '고치라'고만 지시했는데, 고치는 방식(예: Tomcat이 거부한 요청의 `code` 규칙)을 에이전트가 정했다.

## 고려했지만 고르지 않은 것

- DB 스키마와 새 라이브러리 추가도 정책으로 묻기: 사람이 고르지 않았다(2026-11-27). 새 라이브러리는 이미 PR 본문에 이유를 적게 돼 있고, 스키마는 명세의 자원을 따르는 내부 구조라 질문만 크게 늘고 사용자가 겪는 동작은 바뀌지 않는다.
- 범위를 적지 않고 "모호하면 묻는다"만 두기: 지금까지의 규칙이고, 위 근거대로 실패했다.
- 정책 결정을 Issue 코멘트와 `needs-human` 라벨로 넘기기: 세션이 멈췄다가 다시 시작해야 해 느리다. 세션에서 직접 묻고 기다린다.

## 적용과 남은 점

- 새 훅은 두지 않았다(Issue #33 범위 밖). 같은 실수가 다시 나오면 루트 `CLAUDE.md` '환경 개선'에 따라 훅이나 Issue 템플릿을 제안한다.
- 기존 결정 0031~0043은 다시 정하지 않는다. 고칠 부분은 사람이 따로 말한다. 상태만 [0045](0045-decision-status-by-decider.md)로 다시 매겼다.
