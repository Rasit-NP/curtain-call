# 0090. 경로 id는 ASCII 10진 정수 표기만 받는다(공백·16진수·ASCII가 아닌 숫자는 400 INVALID_INPUT, `+2`·`02`는 받는다)

- 상태: 채택
- 날짜: 2026-11-27
- 결정한 사람: 사람. 공백·16진수가 400인 것은 Issue #45 본문의 '이미 정한 정책'으로, `+2`·`02`와 ASCII가 아닌 숫자는 이 Issue 세션에서
  에이전트가 낸 선택지 중 추천을 골랐다(2026-11-27).
- 관련: Issue [#45](https://github.com/Rasit-NP/curtain-call/issues/45), 결정 [0050](0050-performance-detail-id-errors.md), [0072](0072-json-numbers-strict.md), [0091](0091-strict-long-binding.md), spec 3.1, 6.3, 6.5, 6.6

## 결정

- 경로 id(공연 상세의 `performanceId`, 4단계의 `holdId`)는 ASCII 10진 정수 표기(`[+-]?[0-9]+`)이고 long 범위 안일 때만 정수로 본다.
  그 밖은 결정 0050의 '정수가 아님'이라 400 INVALID_INPUT이다.
  - 공백이 들어 있는 값(` 2`, `2 `, `0 2`, `1 0`, 탭 등)과 16진수 표기(`0x2`, `0X2`, `#2`)는 400이다.
  - ASCII가 아닌 숫자(전각 `２`, 아랍-인도 숫자 `٢`, 데바나가리 숫자 `२` 등)는 400이다.
- `+` 부호와 앞자리 0은 받는다. `+2`, `02`, `+02`는 2다. `-0`, `+0`, `00`은 0이라 결정 0050대로 없는 공연(404)이다.

## 근거

- Spring 기본 해석(`NumberUtils.parseNumber`)은 공백을 모두 지우고 `0x`·`#`을 16진수로 읽어, `0x2`·` 2`·`0 2`가 공연 2가 되고 `1 0`은 10이 됐다.
  spec 6.3과 결정 0050은 정수가 아닌 경로 값을 400으로 정했으므로 Issue #45가 이 값들을 400으로 정했다.
- `+2`·`02`: 결정 0050의 'long으로 해석'(`Long.parseLong`)이 받는 표기이고, `-1`을 받는 것과 대칭이다. 프론트엔드는 API가 준 숫자 id만 보내므로 바뀌는 것이 없다.
- ASCII가 아닌 숫자: `Long.parseLong`은 이것도 읽지만(Java 21에서 확인), 정수 표기가 아닌 값을 바꿔 받지 않는다는 점에서 공백·16진수와 같다.
  본문 숫자를 JSON 숫자 그대로만 받는 결정 0072와도 맞다. 프론트엔드는 ASCII 숫자만 보낸다.

## 고려했지만 고르지 않은 것

- `+2`는 400, `02`는 받음 / 둘 다 400(정규 10진 표기만): 사람이 고르지 않았다. 바뀌는 사용자가 없고, 0050의 'long으로 해석'에서 멀어진다.
- ASCII가 아닌 숫자를 받음: 사람이 고르지 않았다.

## 적용과 남은 점

- 구현 방법은 결정 [0091](0091-strict-long-binding.md)(에이전트 결정). 모든 컨트롤러의 long 경로·쿼리 값에 같은 규칙이 적용돼, 4단계 `holdId`도 따로 하지 않아도 된다.
- spec 3.1(공통 400 목록), 6.3 오류 표에 적었다. 6.5·6.6의 `holdId`도 같은 규칙이라고 적었다.
- 테스트: `PerformanceApiTest`(있는 공연의 id를 공백·16진수·ASCII가 아닌 숫자로 쓴 11가지 → 400, `+{id}`·`0{id}`·`00{id}`·`+0{id}` → 200, `-0`·`+0`·`00`·long 범위 끝 → 404,
  long 범위 밖 → 400), `ErrorResponseTest`(공연 상세와 관계없는 시험용 long 경로 값에도 같은 규칙), `StrictLongEditorTest`(단위).
