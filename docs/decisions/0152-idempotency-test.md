# 0152. 멱등 키 테스트: 다시 처리하면 결과가 달라지는 상황에서 같은 키로 보내고, 응답은 상태·Content-Type·본문 문자열로 비교한다. 500은 모의 결제의 '다음 호출 실패'로 만든다

- 상태: 에이전트 결정
- 날짜: 2026-11-28
- 결정한 사람: 에이전트(Issue #56 '에이전트가 정하는 것': 테스트 방법)
- 관련: Issue [#56](https://github.com/Rasit-NP/curtain-call/issues/56), 결정 [0142](0142-payment-impl.md), [0143](0143-payment-concurrency-test-latch.md),
  [0150](0150-idempotency-record-schema.md), [0151](0151-idempotency-impl.md), spec 6.7.1, 6.7.2

## 결정

- **다시 처리하지 않았음을 보이는 방법**: 응답이 처음과 같은 것만으로는 다시 처리했는지 알 수 없다(예: 만료된 선점은 다시 처리해도 409). 그래서 같은 키로 보내기 전에
  다시 처리하면 결과가 달라지는 상황을 만든다.
  - 201 뒤: 선점이 PAID라 다시 처리하면 404.
  - 402 뒤: 거절 지정은 한 번뿐이라 다시 처리하면 201. 선점을 해제하면 404, 만료시키면 409.
  - 404 뒤: 없던 선점 id로 같은 사용자의 선점을 만들어(identity의 다음 값, 테스트가 준비 단언으로 확인) 다시 처리하면 201.
  - 409 뒤: 다시 처리해도 409이므로, 같은 키·다른 선점이 400인지(기록이 남았는지)와 DB의 기록으로 확인한다.
  - 모든 경우에 모의 결제의 호출 횟수, 예매·결제·멱등 기록 행을 함께 본다.
- **같은 응답**: 상태 코드, `Content-Type`, 본문 문자열(UTF-8)이 모두 같다(`PaymentIdempotencyApiTest.assertSameResponse`).
- **같은 키 동시 요청**(`PaymentConcurrencyTest`): 결정 0143의 방법을 쓴다. 요청 5개를 `CountDownLatch`로 함께 출발시키고, 먼저 모의 결제에 들어간 요청이 멈춘 것을 확인한 뒤,
  나머지 넷이 DB 잠금을 기다리는 것을 `pg_stat_activity`로 확인하고 푼다. 응답 5개, 예매·결제·기록 행, 호출 횟수를 본다. 5회 반복한다.
- **500**: 모의 결제에 테스트 조작 `failNext()`(다음 호출 하나에서 예외)를 더한다. 결정 0142처럼 같은 클래스의 메서드이고, 멈추기와 함께 쓰면 풀린 뒤 예외를 던진다.
  통합 테스트 기반이 매 테스트 전에 `reset()`으로 지운다. 같은 키의 먼저 요청이 500으로 끝나고 기다리던 나중 요청이 처음처럼 처리되는 것도 이것으로 만든다.
- **유니크 제약**: 같은 사용자의 결제는 사용자 행에서 한 줄로 서므로 제약을 빼도 동시성 테스트가 실패하지 않을 수 있다. 제약은 스키마 테스트(`IdempotencyRecordSchemaTest`)에서 SQL로 직접 넣어 확인한다.
- **오류 표 3번의 자리**: 저장한 키(201)로 2번에 걸리는 요청(문자열 holdId, 헤더 두 개)을 보내 400인지, 4번이면 404일 요청(결제된 선점, 다른 사용자의 선점)을 보내 저장한 201·400인지 본다.

## 근거

- 결정 0121의 교훈: 테스트가 의도한 상황을 실제로 만들지 못하면 되돌림을 놓친다. 같은 키 재요청은 '처음과 같은 응답'이 다시 처리해도 나올 수 있어 같은 함정이 있다.
  되돌림 확인에서 '저장한 응답 대신 다시 처리'로 바꾸자 409 테스트만 통과했고(다시 처리해도 409), 나머지 R5 테스트 9개가 실패했다. 409 테스트는 그 대신 holdId 비교와 404·409 저장 되돌림에서 실패한다.
- 본문을 문자열로 비교하면 JSON 필드 하나하나를 적지 않아도 '그대로'를 확인한다. 필드 단언은 #55의 결제 테스트가 이미 한다.
- 500을 만들 다른 방법(멈춘 모의 결제의 30초 상한, DB를 테스트 중에 바꾸기)은 느리거나 다른 테스트에 영향을 준다. 테스트 조작은 결정 0142대로 모의 결제 한 곳에 둔다.

## 고려했지만 고르지 않은 것

- 응답의 JSON 필드를 하나씩 비교: 필드가 늘면 놓친다. 문자열 비교가 더 엄격하다.
- 같은 키 동시 요청을 래치 없이 함께 보내기만 함: 먼저 요청이 끝난 뒤에 나중 요청이 출발하면 '기다림'을 확인하지 못한다. 결정 0143처럼 잠금을 기다리는 것을 DB에 묻는다.
- 500을 테스트 설정의 다른 `PaymentGateway` 빈으로 만들기: 결정 0142 '고려했지만 고르지 않은 것'과 같다.

## 적용과 남은 점

- 코드: `PaymentIdempotencyApiTest`, `PaymentConcurrencyTest`(같은 키 2개), `IdempotencyRecordSchemaTest`, `FakePaymentGateway.failNext`, `support/TestPayments`(멱등 기록 조회·삽입).
- 되돌림 확인 결과는 `docs/history/0056-backend-idempotency.md`에 적었다.
- 404 테스트는 선점 id가 identity로 1씩 늘어난다는 데 기댄다. 준비 단언(`없던 선점 id로 선점이 생김`)이 깨지면 테스트가 그 이유로 실패한다.
