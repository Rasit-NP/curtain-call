# 0121. 해제·선점 경합 테스트: 해제를 반복마다 0~10ms 늦게 보내 선점이 먼저 좌석을 잡는 순서도 만든다

- 상태: 에이전트 결정
- 날짜: 2026-11-27
- 결정한 사람: 에이전트(Issue #51 '에이전트가 정하는 것': 테스트 방법)
- 관련: Issue [#51](https://github.com/Rasit-NP/curtain-call/issues/51), 결정 [0100](0100-hold-concurrency-v2.md), [0120](0120-hold-query-release-impl.md), spec 2.4

## 결정

`HoldConcurrencyTest`의 '만료된 선점의 해제와 다른 사용자의 같은 좌석 선점이 동시에 와도 둘 다 성공하고, 새 선점의 좌석은 풀리지 않으며 500이 나지 않는다'는:

- 반복마다 공연을 새로 만들고, A 사용자가 4석을 선점한 뒤 시계를 5분 옮겨 만료시킨다. 그 뒤 A의 해제와 B의 같은 4석 선점(요청 순서는 반대)을 `CountDownLatch`로 함께 출발시킨다.
- 해제는 출발 신호 뒤 `(반복 번호 % 6) × 2`ms(0~10ms)를 기다렸다가 보낸다. 선점은 기다리지 않는다.
- 50회 반복하고, 매번 해제 204·선점 201, A의 선점 RELEASED, 4석 모두 HELD이고 holdId가 B의 선점인지 본다. 실패 메시지에 반복 번호와 기다린 시간을 넣는다.

## 근거

- 처음에는 두 요청을 같은 순간에 보냈다. 해제의 holdId 거르기를 빼는 되돌림 확인에서 이 테스트가 50회 모두 통과했다(순서대로 하는 R3 테스트만 실패).
  해제는 좌석을 잠그기 전 단계(선점 행 하나)가 선점 생성(사용자 행, 공연, 좌석 수, 보유 좌석 수)보다 짧아, 거의 언제나 해제가 먼저 좌석을 잡았기 때문이다.
  그러면 '선점이 먼저 좌석을 잡거나 커밋한 뒤에 해제가 온다'는 순서가 생기지 않아, 테스트 이름이 말하는 '새 선점의 좌석은 풀리지 않는다'를 동시 실행에서 확인하지 못한다.
- 해제를 0~10ms 늦추자 그 순서가 생겼다. 같은 되돌림(거르기 빼기)에서 첫 반복(2ms)에 4석이 모두 풀려 실패했고(1회 실행), 좌석을 잠그지 않고 읽는 되돌림도 첫 반복에서 실패했다(2회 실행).
  지연 0ms인 반복도 남겨 두 요청이 좌석 잠금 단계에서 겹치는 경우도 계속 만든다. 좌석을 id 내림차순으로 잠그는 되돌림은 3회 실행 모두 교착 상태(500)로 실패했다(6, 18, 12번째 반복, 모두 0ms).
- 기다리는 시간은 순서를 섞을 뿐이고, 검증은 어느 순서에서도 같다(둘 다 성공, 최종 상태 같음). 그래서 시간에 따라 결과가 흔들리지 않는다. 원래 코드로 3회 연속 통과했다.

## 고려했지만 고르지 않은 것

- 서비스에 테스트용 대기 지점(래치)을 넣어 순서를 정확히 만들기: 운영 코드에 테스트 전용 지점이 생긴다. 5단계의 결제 경합 테스트는 모의 결제(`FakePaymentGateway`)라는
  원래 있는 지점을 쓰지만, 해제와 선점 생성에는 그런 지점이 없다.
- 반복 횟수만 늘리기: 해제가 거의 언제나 먼저라 횟수를 늘려도 다른 순서가 잘 생기지 않는다.
- 무작위 지연: 실패를 다시 만들기 어렵다. 반복 번호로 정해 실패 메시지의 반복 번호와 지연으로 같은 조건을 알 수 있게 했다.

## 적용과 남은 점

- `HoldConcurrencyTest.concurrently(requests, delaysMillis)`: 요청마다 출발 신호 뒤 기다릴 시간을 받는다. 기존 동시성 테스트는 지연 없이 그대로다.
- 같은 선점의 동시 해제 테스트(5개, 20회 반복)는 지연 없이 보낸다. 선점 행 잠금을 빼는 되돌림에서 첫 반복부터 5개 모두 204가 되어 실패했다.
- 지연 값은 이 환경(로컬 Docker의 PostgreSQL 17, MockMvc)에서 정했다. 기계가 아주 느리거나 빨라도 지연 0ms와 10ms 사이에 두 순서가 모두 생기는지는 되돌림 확인으로만 알 수 있다.
