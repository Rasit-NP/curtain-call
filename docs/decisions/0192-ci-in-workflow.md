# 0192. 작업 흐름: PR 전 로컬 verify.sh 전체는 그대로, PR을 만든 뒤 CI 결과 확인과 실패 수정까지 완료 조건에 넣는다

- 상태: 채택
- 날짜: 2026-11-28
- 결정한 사람: 사람(Issue #67 '아직 정하지 않은 정책' 3번. 이 Issue 세션에서 선택지 셋을 묻고, 사람이 추천안을 골랐다)
- 관련: Issue [#67](https://github.com/Rasit-NP/curtain-call/issues/67), 결정 [0001](0001-verify-single-entry.md), [0183](0183-github-actions.md)

## 결정

- PR을 만들기 전에 로컬에서 `./scripts/verify.sh` 전체를 통과시키는 규칙은 그대로 둔다.
- PR을 만든 뒤 CI 결과를 확인한다. 실패하면 '실패 처리'대로 원인을 찾아 고치고 CI를 다시 통과시킨다. CI 통과가 완료 조건에 들어간다.
- PR 본문의 '검증 결과'에 로컬 검증 요약과 함께 CI 실행 링크와 결과를 적는다.

## 근거

물을 때 보인 근거다.

- 이 Mac에서 로컬 전체 검증은 2분 안팎이고, CI는 1회 6~10분으로 어림했다. 로컬에서 먼저 잡으면 CI 시간을 아끼고 결과도 빨리 본다.
- 로컬에서 통과하고 CI에서만 나는 실패는 운영체제·시간대·로캘 같은 환경 차이다. 이런 실패를 분석해 고치고 기록하는 것도 이 프로젝트가 보여 주려는 과정이다.

## 고려했지만 고르지 않은 것

- CI가 로컬 전체를 대신(PR 전에는 quick만): 로컬 시간은 줄지만 실패를 늦게 알고 CI 시간을 더 쓴다.
- 지금 흐름 그대로(CI 결과는 참고만): CI에서만 나는 실패가 PR에 남은 채 병합될 수 있다.

## 적용과 남은 점

- 루트 `CLAUDE.md`의 '작업 흐름' 4번, 'CI', '실패 처리', '완료 조건'과 `.github/pull_request_template.md`를 고쳤다.
- main 브랜치 보호(CI를 통과해야 병합)는 사람이 설정한다(결정 0183). Free 요금제의 비공개 저장소에서는 브랜치 보호를 쓸 수 없어
  (2026-11-28 `GET /repos/…/branches/main/protection`이 403 "Upgrade to GitHub Pro or make this repository public"), 저장소를 공개로 바꾼 뒤 설정할 수 있다.
  그때까지는 이 규칙과 메인 세션의 결과 확인이 CI 통과를 지킨다.
