# 0065. 프론트: 화면 데이터는 useLoad 훅으로 불러오고, 화면 테스트는 라우터 위치가 아니라 그려진 화면을 기다린다

- 상태: 에이전트 결정
- 날짜: 2026-11-27
- 결정한 사람: 에이전트
- 관련: Issue [#36](https://github.com/Rasit-NP/curtain-call/issues/36), 결정 [0025](0025-msw-unhandled-error-strategy.md), [0042](0042-frontend-guard-test-route.md), [0043](0043-frontend-auth-required-sent-token.md)

## 결정

- 화면에 들어올 때 데이터를 한 번 불러오는 화면은 `src/components/useLoad.ts`의 `useLoad(load)`를 쓴다. 상태는 로딩, 오류(`code`), 받음 셋이다.
  - API 오류(응답 없음 포함)는 `code`로 돌려준다. `AUTH_REQUIRED`도 `code`로 올 뿐이고 로그인 이동은 공통 처리가 한다(0043).
  - `ApiError`가 아닌 예외는 코드 실수로 보고 라우터 오류 화면으로 넘긴다. 화면을 떠난 뒤 온 응답은 버린다.
  - 로딩·오류 문구는 `LoadStatus` 컴포넌트가 그리고, 빈 목록과 목록은 화면이 그린다.
- 테스트 도우미: API별 MSW 핸들러는 `src/test/handlers.ts`, 응답 객체 생성 함수는 `src/test/data.ts`에 둔다. 기본 핸들러는 여전히 두지 않는다(0025).
- 화면 테스트는 화면을 옮긴 뒤 DOM을 검사하거나 조작하기 전에, 옮겨 간 화면의 요소가 그려질 때까지 `findBy…`로 기다린다. `router.state.location`만 기다리지 않는다.

## 근거

- 두 화면의 로딩·오류 처리가 같다(Issue: '로딩과 오류는 공연 목록 화면과 같다'). 훅 하나로 두면 3·4단계 화면도 같은 동작을 쓴다.
- React Router는 화면 이동을 transition으로 그려, 라우터 위치가 바뀐 뒤에도 잠시 이전 화면이 DOM에 남는다. 이 Issue에서 `/`가 빈 화면에서 공연 목록 화면으로 바뀌자, 기존 로그인 화면 테스트가 위치(`/`)만 기다리고 로그인 버튼이 사라졌는지 검사해 전체 실행 15번 중 3번 실패했다. 내 예매 테스트도 `AUTH_REQUIRED` 뒤 이전 화면의 같은 문구를 잡고 바로 로그인 입력을 찾다가 가끔 실패했다. 그려진 화면을 기다리게 고친 뒤 전체 실행 30번 모두 통과했다.

## 고려했지만 고르지 않은 것

- 화면마다 `useEffect`와 상태를 직접 쓰기: 같은 코드가 화면마다 반복되고, 떠난 뒤 응답 버리기를 빠뜨리기 쉽다.
- 라우터의 `loader`로 불러오기: 로딩 상태를 화면 안에 보여 주려면 `defer`·`Suspense`가 필요하고, 가드(`RequireAuth`)가 컴포넌트라 loader가 가드보다 먼저 돈다.
- 테스트에서 transition을 끄기: 실제 앱과 다르게 그려져 이런 문제를 가린다.

## 적용과 남은 점

- `useLoad`의 `load`는 바뀌지 않는 함수여야 한다(바뀌면 다시 불러오지만 로딩 상태로 돌아가지 않는다). 공연 상세처럼 경로 값으로 불러오는 화면(3단계)은 그때 이 점을 다시 본다.
- 개발 모드의 `StrictMode`는 effect를 두 번 실행해 요청이 두 번 나가고, 첫 응답은 버린다. 조회라 문제가 없다.
