# 0134. 프론트: 결제 화면은 라우터 이동을 useBlocker로, 로그아웃을 확인 장치로 막고 해제 판단을 한 함수에 모은다. '뒤로 가기'는 좌석 선택 화면이 남긴 기록 표시로 되돌릴지 정한다

- 상태: 에이전트 결정
- 날짜: 2026-11-28
- 결정한 사람: 에이전트(Issue #52 구현 중 바깥 동작을 바꾸지 않는 구현 방법)
- 관련: Issue [#52](https://github.com/Rasit-NP/curtain-call/issues/52), 명세 7.3·7.8, 결정 [0043](0043-frontend-auth-required-sent-token.md), [0065](0065-frontend-load-hook-and-screen-tests.md), [0082](0082-frontend-seat-selection-impl.md), [0130](0130-frontend-payment-human.md), [0131](0131-frontend-payment-recommended.md), [0132](0132-frontend-late-responses-and-auth-notice.md)

## 결정

- **선점마다 새 화면**: 라우트 요소 `PaymentRoute`가 주소의 선점 번호를 `key`로 `PaymentPage`를 만든다. 선점은 `useLoad`로 불러온다(0065, 0082와 같은 방식).
- **떠나는지 판단하는 두 통로, 판단은 한 함수**:
  - 라우터 이동(브라우저 뒤로가기, 링크, 헤더 메뉴, '뒤로 가기')은 `useBlocker`로 막는다. 막는 조건은 '경로가 바뀌고, 결제 승인이나 해제가 아직 없고, 저장된 토큰이 있음'이다.
  - 로그아웃은 토큰을 먼저 지우므로 `useBlocker`로는 늦다. `src/navigation/leaveGuard.ts`의 확인 장치에 화면이 함수를 등록하고, 헤더의 로그아웃이 토큰을 지우기 전에 `confirmLeave()`로 묻는다.
  - 두 통로 모두 `releaseBeforeLeaving()` 하나로 판단한다. 승인됐거나 해제를 마쳤거나 토큰이 없으면 바로 떠난다. 결제 요청 중이거나 이미 해제 중이면 떠나지 않는다(막음을 푼다). 그 밖에는 해제를 보내고 응답이나 실패를 받은 뒤 떠난다.
  - 막은 이동을 풀거나 진행할 때는 지금의 막음 객체(ref)를 다시 본다. 기다리는 동안 다른 이동이 막음을 풀었을 수 있기 때문이다.
- **렌더링 밖에서 읽는 상태는 ref**: 결제 중, 해제 중, 끝남(승인 또는 해제 완료), 응답을 받지 못한 멱등 키를 ref에 둔다. 버튼이 막히기 전(다시 그리기 전)에 들어온 두 번째 클릭도 막는다.
- **멱등 키**: `crypto.randomUUID()`로 만든다. `ApiError`의 code가 `NO_RESPONSE`가 아니면 다음에 새로 만들고, `NO_RESPONSE`면 다시 쓴다. code 없는 502·503·504도 API 클라이언트가 `NO_RESPONSE`로 넘기므로(0133) 따로 보지 않는다.
- **'뒤로 가기'**: 좌석 선택 화면은 결제 화면으로 보낼 때 기록 state에 `{ fromSeatSelect: true }`를 담는다. 결제 화면은 이 표시가 있으면 `navigate(-1)`(브라우저 뒤로가기와 같음)을, 없으면 그 공연의 좌석 선택 화면으로 `replace` 이동을 한다. 어느 쪽이든 라우터 이동이라 위의 해제를 거친다.
- **해제 함수 공용**: `releaseHoldOnLeave(holdId)`(`src/api/holds.ts`)가 '토큰이 없으면 보내지 않음, 실패해도 넘기지 않음'을 맡는다. 결제 화면과 좌석 선택 화면(떠난 뒤 온 `201`)이 함께 쓴다.
- **AUTH_REQUIRED 문구 감추기**: `isShownOnScreen(code)`(`src/api/errorMessages.ts`) 하나로 `LoadStatus`, 좌석 선택 화면, 결제 화면이 판단한다.
- **테스트 도우미**: `renderApp`이 기록 여러 개(마지막 기록에서 시작)와 `StrictMode`로 그리기를 받는다. 결제·해제·선점 조회의 MSW 핸들러는 토큰이 없으면 서버처럼 401을 준다.

## 근거

- `useBlocker`: 명세 7.3 '구현 주의'. 정리 함수로 판단하면 `StrictMode`에서 들어오자마자 해제된다. 되돌림 확인에서 정리 함수로 바꾸면 StrictMode 테스트가 실패하는 것을 확인했다.
- 로그아웃 확인 장치: 로그아웃을 라우터 이동 뒤로 미루고 도착한 화면이 토큰을 지우게 하면, 기록 state에 남은 표시가 뒤로가기·앞으로가기 때 다시 로그아웃을 일으킬 수 있다. 헤더가 먼저 묻는 편이 단순하고 순서(해제 → 토큰 삭제 → 이동)가 코드에 그대로 드러난다.
- 판단 한 곳: 두 통로가 같은 규칙(결제 중 막기, 해제를 기다림, 토큰 없으면 해제 안 함)을 따라야 한다. 규칙이 두 군데 있으면 하나만 고쳐질 수 있다.
- '뒤로 가기'의 기록 표시: 앞 기록이 무엇인지는 라우터가 알려 주지 않는다. 늘 `navigate(-1)`이면 주소로 바로 들어왔을 때 앱 밖으로 나가고, 늘 push면 기록이 '좌석 → 결제 → 좌석'으로 쌓여 뒤로가기가 해제된 결제 화면(404)으로 간다. `location.key`로 첫 기록인지 보는 방법은 가드·로그인 뒤의 `replace` 이동에서 맞지 않는다.

## 고려했지만 고르지 않은 것

- `useEffect` 정리 함수로 해제: 위 이유.
- 결제 화면이 아닌 헤더가 결제 화면 상태를 직접 보기: 헤더가 화면마다의 규칙을 알아야 한다.
- 시계(남은 시간)와 응답 `Date` 헤더 보정: 사람이 시계를 빼기로 해(0130) 만들지 않았다.

## 적용과 남은 점

- 해제 중에 토큰이 만료돼 해제가 `AUTH_REQUIRED`를 받으면, 공통 처리의 로그인 이동과 막아 둔 이동의 진행이 겹친다. 마지막으로 처리된 이동의 화면이 보인다. 토큰(1시간)이 결제 화면에 머무는 그 순간 만료되는 드문 경우라 따로 막지 않았다.
- 해제를 마쳤는데 막아 둔 이동이 그 사이 다른 이동으로 풀렸으면 결제 화면에 남는다. 이때 '결제하기'는 해제 중 상태로 막혀 있고, 다른 곳으로는 막힘 없이 이동한다.
- 멱등 키를 만드는 `crypto.randomUUID()`(명세 7.3)는 보안 컨텍스트(https, localhost)에서만 있다. 개발 서버를 LAN 주소(http)로 열면 없어서 '결제하기'가 라우터 오류 화면으로 넘어간다. 개발·E2E는 localhost로 돌고 배포는 범위 밖이라 대체 생성을 두지 않았다(PR #54 리뷰 지적).
- 브라우저 뒤로가기 막기는 메모리 라우터 테스트로만 확인했다. 개발 서버의 실제 브라우저 확인은 이 Issue의 범위가 아니어서 하지 않았다(E2E 6단계).
