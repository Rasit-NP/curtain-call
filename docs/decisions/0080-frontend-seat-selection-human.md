# 0080. 프론트: 좌석 선택 화면 — 범례 두 가지, 표시 이름 A3, 409는 선택을 비우고 다시 불러오기, 5번째 좌석은 눌러도 선택되지 않음

- 상태: 채택
- 날짜: 2026-11-27
- 결정한 사람: 사람(2026-11-27 Issue #42 세션에서 에이전트가 물은 정책에 직접 답함)
- 관련: Issue [#42](https://github.com/Rasit-NP/curtain-call/issues/42), 명세 2.1·7.2·7.4, 결정 [0081](0081-frontend-seat-selection-recommended.md)

## 결정

사람이 자기 말로 정한 것만 적는다. 같은 질문에서 추천을 맡긴 부분은 [0081](0081-frontend-seat-selection-recommended.md)에 있다.

- **범례**: 좌석 상태 범례는 '선택 가능'·'선택 불가' 두 가지만 둔다. 사람의 답: "선택가능 · 선택 불가만 볼 수 있습니다."
- **좌석 표시 이름**: `A3`처럼 줄과 번호를 붙여 쓴다. 사람의 답: "`A3`으로 진행합니다."
- **선점 요청이 409일 때**(다른 사람이 먼저 잡은 경우): 고른 좌석을 비우고, 잡힌 좌석을 '선택 불가'로 보여 주며, 좌석 정보를 서버에서 다시 받아온다. 그 밖의 오류는 고른 좌석을 그대로 둔다.
  사람의 답: "409의 경우는 선택을 비우고, 해당 좌석을 선택불가 표기. 이외의 경우는 좌석을 그대로 둡니다. 409의 경우, 백엔드에서 다시 좌석 정보를 받아와야 합니다."
- **5번째 좌석**: 4석을 고른 뒤에는 5번째 좌석이 어떤 경우에도 선택되지 않는다. 남은 좌석은 누를 수 있지만 눌러도 선택되지 않고 `HOLD_LIMIT_EXCEEDED` 문구가 뜬다.
  사람이 "애초에 5개 좌석을 선택할 수 없도록 해주세요"라고 요청했고, 에이전트가 막는 방식 두 가지(눌러도 선택 안 됨 / 아예 누를 수 없게)를 물어 사람이 '눌러도 선택 안 됨'을 골랐다. 명세 7.2가 원래 정한 동작과 같다.
- **결제 화면에서 뒤로가기**: 좌석 선택 화면으로 돌아가면 선점은 풀린다. 사람의 답: "결제 화면에서 뒤로가기를 눌러 좌석 선택 화면으로 돌아간다면, 선점은 풀립니다." 명세 7.3에 이미 있는 동작이고 결제 화면(4단계)에서 만든다.

## 근거

- 사람이 정했다. 에이전트가 물을 때 든 근거는 [docs/history/0042](../history/0042-frontend-seat-selection.md)의 '정책 결정(사람)'에 있다.

## 고려했지만 고르지 않은 것

- 범례 네 가지(선택 가능·선택됨·선점됨·판매됨), 선점됨·판매됨 두 가지, 범례 없음.
- 표시 이름 `A-3`(그때까지의 명세), 번호만(`3`), 글자 없이 색만.
- 409 뒤 고를 수 없게 된 좌석만 빼고 나머지 선택은 남기기(그때까지의 명세 7.2).
- 4석을 고르면 남은 좌석을 모두 '선택 불가'로 바꿔 누를 수 없게 하기: 누를 때 이유를 알려 줄 수 없다.

## 적용과 남은 점

- 명세 2.1·5·7.2·7.4·8과 `frontend/CLAUDE.md`의 예시를 `A3`, '선택 불가'로 고쳤다. 지난 결정 파일(0047 등)의 `A-3` 예시는 고치지 않는다.
- 표시 이름은 `src/format.ts`의 `seatName`으로 모든 화면이 함께 쓴다. 내 예매 화면도 `좌석 A1, A2`로 바뀌었다.
- 결제 화면(4단계)에 넘길 점: 뒤로가기로 좌석 선택 화면에 돌아오면 좌석 상태를 새로 불러온다. 이 요청이 선점 해제보다 먼저 처리되면 방금 내 좌석이 잠시 '선택 불가'로 보일 수 있다.
