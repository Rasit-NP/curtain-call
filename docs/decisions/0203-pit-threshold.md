# 0203. 뮤테이션 점수 기준: 보강 후 재측정 점수의 소수점 버림(93%)보다 낮으면 실패한다. 실패시키는 곳은 verify.sh mutation과 수동 실행 워크플로

- 상태: 채택
- 날짜: 2026-11-28
- 결정한 사람: 사람(Issue #69 '아직 정하지 않은 정책' 2번. 첫 측정 뒤 이 Issue 세션에서 선택지 셋을 묻고, 사람이 추천안을 골랐다). 기준값 93은 이 규칙대로 재측정 뒤 에이전트가 넣었다
- 관련: Issue [#69](https://github.com/Rasit-NP/curtain-call/issues/69), 결정 [0200](0200-pit-setup.md), [0202](0202-pit-when-to-run.md)(실행 시점),
  [0204](0204-pit-survivor-classification.md)(분류)

## 결정

- 뮤테이션 점수(죽인 변이 / 전체 변이, 덮이지 않은 변이 포함)가 기준값보다 낮으면 실패한다. PIT의 `mutationThreshold`(`backend/build.gradle`)로 건다.
- 기준값은 테스트를 보강한 뒤 같은 명령·설정으로 다시 잰 점수의 소수점 버림이다. 재측정 점수가 93.3%(209개 중 195개)라 **93**이다.
- 실패시키는 곳은 결정 0202의 실행 지점, 곧 `./scripts/verify.sh mutation`(로컬)과 수동 실행 워크플로 `mutation.yml`이다. PR CI와 `verify.sh` 전체에는 PIT가 없으므로 그곳은 실패시키지 않는다.
- 테스트 강도(죽인 변이 / 덮인 변이)와 줄 커버리지에는 기준을 두지 않는다.

## 근거

물을 때 보인 근거다.

- 같은 설정으로 두 번 잰 기준선이 변이 하나하나의 판정까지 같았다. 동시성 테스트도 시간 초과 없이 돌았다. 점수가 흔들리지 않으므로 실패는 곧 '새로 살아남은 변이'이고 바로 분석할 수 있다.
- 보강 뒤 남은 14개는 하나씩 이유를 적은 것(동등 변이, 도달할 수 없는 코드, PIT가 재지 못하는 스프링 시작 코드, 검증할 가치가 낮은 문구)이라, 기준값을 그보다 낮출 까닭이 없다.
- 측정 대상 클래스에 코드를 더하면 새 변이도 죽여야 통과한다. 규칙 코드를 바꾸는 PR(3단계 인증, 5단계 예매 취소)에서 테스트 보강을 강제한다.

## 고려했지만 고르지 않은 것

물을 때 보인 선택지다.

- 기록만: 실패시키지 않고 점수와 분류를 보고서에만 적는다. 퇴보는 사람이 리포트를 보고 알아챈다.
- 낮은 기준값(기준선 86%): 큰 퇴보만 잡고 새로 살아남은 변이 몇 개는 통과한다.

## 적용과 남은 점

- PIT 1.30.2는 점수를 정수로 반올림(HALF_UP)한 뒤 기준값과 비교한다(`PercentageCalculator`, Gradle 플러그인은 소수 자릿수 설정을 넘기지 않는다).
  그래서 지금 변이 수(209개)에서는 새로 살아남은 변이가 1개면 194/209 = 92.8% → 93으로 통과하고, 2개 이상이면 실패한다. 변이 수가 바뀌면 이 경계도 바뀐다.
- 기준값을 넘긴 확인: 기준값을 잠시 94로 올려 `verify.sh mutation`이 실패하고 실패 요약에 PIT의 'Mutation score of 93 is below threshold of 94'가 보이는 것을 확인했다(진행 기록 #69).
- 기준값을 바꾸면 이 결정을 바꾸는 것이라 새 결정 기록을 남긴다. 기준값을 내리는 것(예: 측정 대상에 클래스를 더해 동등 변이가 늘 때)은 사람에게 묻는다.
