# 0071. 토큰의 사용자가 DB에 없으면 따로 처리하지 않는다(선점을 저장할 때 외래 키가 막아 500)

- 상태: 채택
- 날짜: 2026-11-27
- 결정한 사람: 사람(2026-11-27, Issue #41 세션). 에이전트가 선택지와 추천을 냈다.
- 관련: Issue [#41](https://github.com/Rasit-NP/curtain-call/issues/41), 결정 [0038](0038-jwt-validation-v2.md), [0039](0039-current-user-id-v2.md), [0073](0073-hold-concurrency.md), spec 2.4, 3.1

## 결정

선점을 만들 때 토큰(서명·만료가 정상)의 사용자(`sub`)가 `users`에 없으면 따로 처리하지 않는다.
같은 사용자의 요청을 한 줄로 세우는 사용자 행 잠금은 잠글 행이 없어 그냥 지나간다. 앞 검사(404, 409)에 걸리지 않으면 선점을 저장할 때
외래 키가 막아 500 INTERNAL_ERROR가 되고, 트랜잭션이 되돌려져 아무 좌석도 선점되지 않는다.

## 근거

- 토큰 검증은 서명·만료만 보고 DB를 보지 않는다(결정 0038). 사용자가 있는지 따로 확인하면 토큰을 DB로 검증하는 셈이다.
- 사용자를 지우는 기능이 없어 정상 흐름에서는 생기지 않는다. 예상하지 못한 상황이므로 spec 3.1의 500이다.

## 경위

처음에는 "토큰은 정상인데 그 사용자(sub)가 DB에 없으면 POST /api/holds는 무엇으로 응답할까"라고 묻고,
401 AUTH_REQUIRED(추천), 404 NOT_FOUND, 따로 처리하지 않음(500)을 내놓았다.
사람은 "토큰을 DB에서 검증하나요?? 그럼 뭐하러 토큰을 사용하나요?"라고 되물었다. 질문이 토큰 검증 방식을 바꾸자는 말로 읽힌 것이다.
토큰 검증은 그대로이고, 선점이 같은 사용자의 요청을 한 줄로 세우려고 사용자 행을 잠그며(spec 2.4의 예) `user_id`를 외래 키로 저장해서 생긴 질문이라고 밝힌 뒤
다시 물었다(따로 처리하지 않음(추천) / 사용자 행에 기대지 않음). 사람이 '따로 처리하지 않음'을 골랐다.

## 고려했지만 고르지 않은 것

- 401 AUTH_REQUIRED: '사용자 행이 없음'을 '토큰이 잘못됨'으로 바꿔 읽는다. 토큰을 DB로 검증하는 것과 같다.
- 404 NOT_FOUND: spec 6.4의 404(공연·좌석이 없음)와 뜻이 다르다.
- 사용자 행에 기대지 않음(사용자 id로 PostgreSQL advisory lock을 걸고 `user_id`에 외래 키를 두지 않음): 없는 사용자 id로도 선점이 만들어진다.

## 적용과 남은 점

- 테스트: '토큰의 사용자가 DB에 없으면 따로 처리하지 않아 500 INTERNAL_ERROR이고 아무 좌석도 선점되지 않는다'(`HoldApiTest`).
- 결제(5단계)도 예매에 사용자 id를 외래 키로 저장하면 같은 경우가 생긴다. 이 결정을 따른다.
