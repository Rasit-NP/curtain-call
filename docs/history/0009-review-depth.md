# #9 리뷰 강도를 PR 위험도에 맞추기

- 기간: 2026-11-26
- Issue: [#9](https://github.com/Rasit-NP/curtain-call/issues/9), PR: [#10](https://github.com/Rasit-NP/curtain-call/pull/10) (병합 전)
- 관련 결정: [0023](../decisions/0023-review-depth-by-risk.md)

## 무슨 일이 있었나

사람이 PR #7(프론트엔드 첫 설정)과 #8(백엔드 첫 설정)의 리뷰를 요청했다. 에이전트는 `/code-review`를 강도 없이 호출했고, 도구는 마지막에 입력된 강도인 `max`를 그대로 썼다. 그 결과는 다음과 같았다.

- PR마다 리뷰 관점 에이전트 6개(줄 단위, 삭제된 동작, 파일 간 추적, 언어 함정, 래퍼, 규칙)를 돌렸다.
- 후보마다 검증 에이전트를 따로 띄웠다. PR #7은 15개였다.
- 이미 리뷰 에이전트 5개가 각자 재현한 후보도 다시 검증했다.

R1~R6을 하나도 구현하지 않는 골격 PR 두 건에 에이전트 약 35개가 쓰였고, 하나에 5~20분씩 걸렸다. 사람이 "초기 설정 PR에 왜 이렇게 오래 걸리나"라고 물었다.

## 원인 분석

1. **강도를 위험도가 아닌 기억된 설정으로 정했다.** 하네스에 리뷰 강도 규칙이 없었다.
2. **같은 검증을 두 번 했다.** 리뷰 단계에서 이미 재현된 후보를 검증 단계에서 다시 재현했다.
3. **멈출 기준이 없었다.** 중요한 결함이 나온 시점에서 보고하고 물을 수 있었다.

## 판단과 근거

- **처음 제안은 "리뷰 강도를 일괄로 낮춘다"였다.** 사람이 "AI 리뷰는 꼼꼼해야 한다. 문제는 골격 PR에 지나친 시간을 쓴 것"이라고 바로잡았다.
- 그래서 **위험도에 비례하게** 바꿨다([0023](../decisions/0023-review-depth-by-risk.md)). 규칙 코드는 `high`, 일반 기능은 `medium`, 골격·설정·문서는 `low`로 둔다. 재현된 후보는 다시 검증하지 않고, 중요한 결함이 나오면 먼저 보고한다.
- **훅으로 강제하지 않았다.** 규칙만으로 부족하면 그때 추가한다.
- **진행 중이던 PR #8 후보 검증은 중단했다.** 핵심 결함은 이미 여러 에이전트가 따로 재현했다.

## 결과

루트 `CLAUDE.md`에 '리뷰' 절을 추가했다. 이 기록은 [`docs/agent-log.md`](../agent-log.md)에도 한 줄로 남겼다.

## 배운 점

- 같은 리뷰 강도라도 PR 종류에 따라 비용 대비 가치가 크게 다르다. 강도는 대상의 위험도로 정해야 한다.
- 도구의 '기억된 설정'은 의도하지 않은 비용을 만든다. 매번 명시하는 규칙이 필요하다.
