# #45 백엔드 입력 검증 보강: 경로 id 엄격 해석(결정 0050), 좌석 row 정렬 통합 테스트

- 기간: 2026-11-27
- Issue: [#45](https://github.com/Rasit-NP/curtain-call/issues/45), PR: [#50](https://github.com/Rasit-NP/curtain-call/pull/50)
- 관련 결정: [0090](../decisions/0090-path-id-ascii-decimal.md), [0091](../decisions/0091-strict-long-binding.md). 기존 [0050](../decisions/0050-performance-detail-id-errors.md)을 구체화한다(바꾸지 않는다)

## 배경

3단계(선점)가 병합된 뒤 메인 세션이 프로젝트를 점검했다(2026-11-27). `./scripts/verify.sh` 전체와 실제 앱 연동은 정상이었지만,
백엔드에서 결함 하나와 테스트 공백 하나를 찾았다. 로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 '3단계 뒤 점검 수정' 단계로,
문서 Issue(#46), 프론트엔드 테스트 Issue(#47)와 동시에 진행한다. 이 Issue는 `backend/`와 `docs/`만 고치고, 결정 번호는 0090부터 쓴다.

1. **경로 id를 느슨하게 해석한다.** `@PathVariable long performanceId`가 Spring 변환기(`NumberUtils.parseNumber`)를 거치면서
   공백을 모두 지우고 `0x`·`#`로 시작하면 16진수로 읽는다. `0x2`, `#2`, ` 2`, `2 `, `0 2`가 공연 2가 되고, `1 0`은 10이 된다.
   명세 3.1·6.3과 결정 0050은 정수가 아닌 경로 값을 400 INVALID_INPUT으로 정했다. 4단계의 `holdId`도 같은 방식이 되므로 그 전에 고친다.
2. **좌석 row의 코드 포인트 순서를 지키는 통합 테스트가 없다.** V2 마이그레이션의 `seat_row ... COLLATE "C"`가 좌석 목록을 명세 5의 순서로 만드는데,
   점검 에이전트가 이것을 빼고 돌려도 통합 테스트가 모두 통과했다. 그때 `a`·`B` 좌석의 순서는 공연 상세가 `a, B`, 선점 응답이 `B, a`로 어긋났다.
   대응표의 '좌석(5)' 행은 이것을 자바 비교만 보는 단위 테스트(`SeatOrderTest`)에 걸어 두었다.

## 판단과 근거

사람이 정한 것(2026-11-27, 이 Issue 세션):

- **부호와 앞자리 0**: `+2`, `02`는 지금처럼 받는다(공연 2). `-0`, `+0`, `00`은 0이 되어 404다.
  선택지(둘 다 받음 / `+2`만 400 / 둘 다 400)와 추천(둘 다 받음: 결정 0050의 'long으로 해석'과 같고, `-1`을 받는 것과 대칭이며, 프론트엔드는 API가 준 숫자만 보낸다)을 함께 물었고, 사람이 추천을 골랐다.
- **ASCII가 아닌 숫자**: 전각 `２`, 아랍-인도 숫자 `٢`, 데바나가리 숫자 `२`는 400 INVALID_INPUT이다.
  Issue 본문에는 없던 경우다. `Long.parseLong`이 이 숫자들도 2로 읽는 것을 Java 21에서 확인해, 지금 `/api/performances/２`가 공연 2로 해석된다는 것을 알았다.
  선택지(400 / 받음)와 추천(400: 공백·16진수를 막는 이유와 같고, 본문 숫자를 엄격하게 받는 결정 0072와 맞으며, 프론트엔드는 ASCII 숫자만 보낸다)을 함께 물었고, 사람이 추천을 골랐다.

두 답을 합치면 경로 id는 "ASCII 10진 정수 표기(`[+-]?[0-9]+`)이고 long 범위 안"이어야 한다([0090](../decisions/0090-path-id-ascii-decimal.md), 채택).

에이전트가 정한 것(Issue 본문 '에이전트가 정하는 것'):

- **해석을 한곳에**([0091](../decisions/0091-strict-long-binding.md)): `StrictLongEditor`(PropertyEditor)가 규칙대로 해석하고,
  `@ControllerAdvice`인 `StrictLongBinding`이 모든 컨트롤러의 바인더에 `long`·`Long`용으로 등록한다. 4단계의 `holdId`는 `long`으로 받기만 하면 같은 규칙이 된다.
  해석에 실패하면 지금처럼 인자 형식 오류가 되고 공통 처리기가 400 INVALID_INPUT으로 바꾸므로, 오류 처리 코드는 늘지 않는다.
  컨트롤러마다 `String`으로 받아 해석하는 방법은 holdId에서 잊을 수 있고, 전용 애너테이션과 인자 해석기는 `@PathVariable`의 동작을 다시 만들어야 해서 고르지 않았다.
- **테스트 방법**: MockMvc 통합 테스트와 해석기 단위 테스트. 공연 상세 테스트는 고정 문자열(`0x2`) 대신 테스트가 만든 공연의 id를 바꿔 쓴 값을 보낸다.
  느슨하게 해석하면 그 공연(200)이 되므로, 결함이 '다른 공연을 보여 준다'는 것을 실패 메시지로 바로 볼 수 있다. id 값(시퀀스)에 기대지도 않는다.
  공연 상세와 관계없는 시험용 경로 값 테스트는 규칙이 공연 상세 한곳의 처리가 아니라는 것을 보인다.
- **좌석 정렬 테스트**: 대소문자가 섞인 row(`a`, `B`, `A`)에 U+FFFD와 보충 문자(U+1F3AD)를 더해, 공연 상세(DB 정렬)와 선점 응답(자바 정렬)을 같은 테스트에서 비교한다.
  보충 문자는 UTF-8 바이트 순서(`COLLATE "C"`)와 코드 포인트 순서(`SeatOrder`)가 같다는 것까지 실제 DB로 확인하려고 넣었다.

## 실패와 수정

- **변환 서비스에 더한 변환기가 효과가 없었다.** 처음에는 `WebMvcConfigurer.addFormatters`로 엄격한 `Converter<String, Long>`을 등록했다.
  단위 테스트는 통과했는데 통합 테스트 17개가 그대로 200(또는 404)이었다.
  가설: "등록한 변환기가 `@PathVariable long` 변환에 쓰이지 않는다." 임시 테스트로 MVC 변환 서비스를 직접 불러 보니 변환기는 등록돼 있었고 `0x2`를 거부했다.
  바인더도 같은 변환 서비스를 쓰고 있었다. 원인은 바인더(`TypeConverterDelegate`)가 변환 서비스의 실패를 받으면 기본 편집기(`CustomNumberEditor` → `NumberUtils.parseNumber`)로
  다시 해석하는 것이었다. 예전에도 `abc`는 두 방법 모두 실패해서 400이었고, `0x2`는 두 번째 방법이 받아들였다.
  바인더에 직접 등록한 편집기는 변환 서비스보다 먼저 쓰이고 다시 해석하지 않으므로, 변환기를 지우고 편집기로 바꿨다(두 번째 시도에서 해결). 임시 테스트는 지웠다.

  `0x2`·` 3`이 2·3이 된다. 결정 0091과 Javadoc은 '`@RequestParam long`(Long 포함) 모두'라고 적어 이것까지 엄격하다고 읽혔다.
  리뷰는 실행해서 재현하지 않았으므로 임시 테스트로 확인했다(단일 `Long`은 400, 감싼 타입 셋은 200. 테스트는 지웠다).

  감싼 타입이 생기면 그때 정한다는 것을 적었다. 동작은 바꾸지 않았다.
