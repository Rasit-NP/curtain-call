# #52 프론트엔드 결제·예매 확인 화면(R3·R4·R5·R6): 선점 불러오기, 남은 시간, 결제와 멱등 키, 떠날 때 선점 해제

- 기간: 2026-11-27 ~
- Issue: [#52](https://github.com/Rasit-NP/curtain-call/issues/52), PR: (작성 전)
- 관련 결정: [0130](../decisions/0130-frontend-payment-human.md), [0131](../decisions/0131-frontend-payment-recommended.md), [0132](../decisions/0132-frontend-late-responses-and-auth-notice.md), [0133](../decisions/0133-frontend-error-fallback-v2.md)

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 4단계 프론트엔드다. 결제·예매 확인 화면(`/holds/:holdId`)을 만든다.
선점을 불러와 남은 시간을 보여 주고, '결제하기'로 결제하며, 결제가 승인되기 전에 앱 안의 다른 화면으로 가면 선점을 해제한다(명세 1장 5번, 7.3).

좌석 선택 화면(#42)은 선점에 성공하면 `/holds/{id}`로 이동하지만, 그 화면이 없어 라우터 기본 404 화면이 뜬다.
백엔드 선점 조회·해제(#51)는 다른 세션에서 동시에 진행하고, 결제 API는 5단계에서 생긴다. 그래서 세 API는 MSW로 흉내 낸다.
로드맵의 '결제 화면 Issue로' 절에서 넘겨받은 미정 정책 4개(선점 요청 중 좌석 선택 화면을 떠날 때, 로그인 요청 중 떠날 때, 개발 서버의 본문 없는 502, `AUTH_REQUIRED` 문구가 잠깐 보이는 것)도 이 Issue에서 정한다.

## 진행

- 메인 세션이 Issue를 만들고 이 Issue용 워크트리 세션을 시작했다. 워크트리 브랜치는 이미 `origin/main`(`c947d05`)과 같아 맞출 것이 없었고, 이름만 `feat/52-frontend-payment`로 바꿨다.
- 정책 답을 기다리는 사이 #51(PR #53)이 병합됐다. 진행 기록 첫 커밋을 `origin/main`에 rebase하면서 진행 기록 목차의 충돌(#51과 #52 행)을 두 행 모두 남겨 풀었다. PR #53은 명세를 바꾸지 않아 선점 조회·해제 API는 명세 6.5·6.6대로 흉내 낸다.
- Issue의 '아직 정하지 않은 정책' 12개(결제 화면 표시 5, 떠날 때의 해제 3, 로드맵에서 넘겨받은 것 4)와, 명세·Issue를 읽다 찾은 화면 동작 질문을 구현 전에 이 세션에서 사람에게 한 번에 물었다.

## 정책 결정(사람)

구현 전에 15개를 한 번에 물었다. 1~12는 Issue가 '아직 정하지 않은 정책'으로 남긴 것(결제 화면 표시 5, 떠날 때의 해제 3, 로드맵에서 넘겨받은 것 4)이고, 13~15는 명세와 Issue를 읽다 찾은 화면 동작('좌석 다시 선택'을 언제 보일지, `404`·`409` 뒤 결제 버튼, 문구를 지우는 때)이다. 항목마다 선택지·추천·근거를 쓰고, 명세 용어 '안내 문구'는 '화면에 빨간 글씨로 뜨는 알림'이라고 예를 들어 설명했다.

- **첫 답**: 13개는 "추천대로". 두 개는 사람이 자기 말로 답했다.
  - 3번(남은 시간이 0이 되면, 추천은 `EXPIRED`와 같은 화면으로 바꾸고 결제 버튼을 지움): "프론트에서 보여주는 시계가 서버와 동일하란 보장이 없지 않나요? 결제 버튼은 남겨두되, 결제가 불가능하도록 처리합니다. 이 때, 시간이 초과되었다는 메시지를 보여줍니다."
  - 13번('좌석 다시 선택'을 결제 전에 늘 둘지): "'다시 선택'이라고 명시되어 있는 버튼은 없습니다. 결제 화면에서 '뒤로 가기' 혹은 '취소' 형태로 보이게 만듭니다."
- **다시 물은 세 개**: 두 답 때문에 정해지지 않은 점이 생겨 구현하지 않고 다시 물었다.
  - 버튼 이름: '뒤로 가기'(추천)와 '취소' 중 무엇으로 할지. 사람이 '뒤로 가기'를 골랐다.
  - 서버가 만료를 알려 준 경우(들어올 때 `EXPIRED`, 결제 응답 `409`)의 결제 버튼: 3번 답은 화면 시계로 판단한 경우라 이 경우는 정해지지 않았다. 사람은 고르는 대신 "굳이 시계를 보여줘야 하나요? 걍 보여주지 말죠. 제한 시간 안에 결제해야 한다는 문구 정도면 충분하지 않을까요?"라고 답했다.
  - 0초가 됐을 때 시계 줄을 남길지: "화면 시계 걍 빼죠".
- **세 번째로 물은 세 개**: 시계를 빼면 Issue와 명세가 '이미 정한 정책'으로 둔 'R3: 남은 시간이 0이 되면 화면이 버튼을 막는다'가 바뀐다. 그래서 시간이 다 된 것을 누가 판단할지(서버만 / 보이지 않게 셈), 만료가 확인됐을 때 결제 버튼(남기고 막음 / 두지 않음), 시계 대신 둘 문구(시간 없는 문장 / 마감 시각)를 물었다. 사람은 셋 다 추천을 골랐다.
- **기록**: 사람이 자기 말로 정했거나 선택지에서 고른 것(시계 없음과 서버만 판단, 만료 때 버튼을 남기고 막음, 제한 안내 문구, '뒤로 가기')은 [0130](../decisions/0130-frontend-payment-human.md)에 `채택`으로 적었다. "추천대로" 맡긴 것은 결제 화면 [0131](../decisions/0131-frontend-payment-recommended.md), 넘겨받은 정책 [0132](../decisions/0132-frontend-late-responses-and-auth-notice.md)·[0133](../decisions/0133-frontend-error-fallback-v2.md)에 `에이전트 결정`으로 적었다(0045). 0133은 0018을 일부 바꾸므로 0018을 `대체됨(→0133)`으로 바꿨다.
  처음에 "추천대로"였던 2번(남은 시간 형식)과 4번(기준 시계를 응답의 `Date` 헤더로 보정)은 시계를 빼면서 쓸 일이 없어졌다.
- 답은 명세 3.3·7.1·7.2·7.3·7.5·7.6·7.8에 반영했다.

## 구현 중 판단과 근거(에이전트)

- **API 함수**: `getHold`(GET), `releaseHold`(DELETE), `createPayment`(POST, `Idempotency-Key` 헤더)를 모두 `auth: true`로 만들고 결제 응답 타입 `PaymentResult`를 더했다. 선점 번호는 주소에서 받은 문자열을 `encodeURIComponent`로 경로 한 칸에만 넣는다(`getPerformance`와 같다).
- **떠날 때의 해제 함수**: '토큰이 없으면 보내지 않음, 실패해도 넘기지 않음'을 `releaseHoldOnLeave` 하나에 두고 결제 화면과 좌석 선택 화면(떠난 뒤 온 `201`)이 함께 쓴다. 토큰 없이 보내면 그 401이 공통 처리를 불러, 로그아웃한 사용자를 로그인 화면으로 보내기 때문이다(0043).
- **떠나는지 판단**([0134](../decisions/0134-frontend-payment-impl.md)): 라우터 이동은 `useBlocker`, 로그아웃은 새 확인 장치(`src/navigation/leaveGuard.ts`)로 받는다. 로그아웃은 토큰을 먼저 지워 `useBlocker`로는 늦기 때문이다. 둘 다 `releaseBeforeLeaving()` 하나로 판단한다(결제 중이면 머묾, 해제를 기다린 뒤 이동, 토큰이 없으면 해제 없이 이동).
- **'뒤로 가기'**: 좌석 선택 화면이 결제 화면으로 보낼 때 기록 state에 표시를 남기고, 결제 화면은 표시가 있으면 기록을 되돌리고(브라우저 뒤로가기와 같음) 없으면 좌석 선택 화면으로 `replace`한다. 늘 push하면 기록이 '좌석 → 결제 → 좌석'으로 쌓여 뒤로가기가 해제된 결제 화면으로 간다.
- **code 없는 502·503·504**([0133](../decisions/0133-frontend-error-fallback-v2.md)): API 클라이언트에서 `NO_RESPONSE`로 바꾸고 `status`는 받은 값을 남겼다. 기존 테스트 6개(클라이언트 2, 로그인·공연 목록·좌석 선택 화면 4)가 'code 없는 502 → 일시적인 오류'를 기대했다. 이 테스트들이 확인하려던 것은 'code 없는 오류 응답의 대체 code'이므로 상태를 500으로 바꿔 뜻을 지키고, 502·503·504의 새 테스트를 더했다. 사람이 정한 명세 변경(11번 "추천대로")에 따른 기대값 변경이다.
- **AUTH_REQUIRED 문구**: `isShownOnScreen` 하나로 `LoadStatus`·좌석 선택·결제 화면이 판단한다. 그리는 순간이 짧아 테스트로 잡기 어려워서, 다시 로그인한 뒤에 끝난 이전 요청(공통 처리가 화면을 옮기지 않는 경우, 0043)으로 '그 화면에 문구가 없다'를 확인했다.
- **좌석 선택 화면의 기존 테스트 4개**: `201` 뒤 `/holds/31`로 이동하면 이제 실제 결제 화면이 선점을 불러온다. 이 요청의 MSW 핸들러만 더했고 기대값은 바꾸지 않았다.
- **새 라이브러리 없음**.

## 실패와 수정

- **테스트를 먼저 쓰고 실패 확인**: API 함수 테스트 14개(함수 없음, 502·503·504 처리 없음)와 결제 모듈 없음 1파일, 화면 테스트 42개(결제 화면 37, 떠난 뒤 온 선점·로그인 응답 2, AUTH_REQUIRED 문구 3)가 실패하는 것을 확인한 뒤 구현했다. '로그아웃 뒤 늦게 온 선점은 해제하지 않는다'는 지금 코드가 응답을 버리고 있어 처음부터 통과했다. 토큰 확인을 빠뜨린 구현을 잡는 테스트라 그대로 두었다.
- **구현 뒤 첫 실행**: 프론트엔드 테스트 220개가 모두 통과했다. 타입 검사와 린트도 통과했다.
- **R3 테스트 보강**: '화면은 시간을 세지 않는다' 테스트가 처음에는 들어올 때 기기 시계가 만료 1초 전이었다. 그러면 그리는 순간에 시각을 한 번만 비교하는 구현은 잡지 못한다. 들어올 때부터 기기 시계가 만료 시각을 지난 경우(서버는 `ACTIVE`)로 바꾸고, 시간을 더 흘려도 막지 않는 것까지 보게 했다.
- **안정성 확인**: 되돌림 확인 전에 프론트엔드 전체 테스트를 15번 돌려 모두 통과했다. 그래서 아래 되돌림 결과의 실패는 불안정함이 아니라 되돌린 코드 때문이다.
- **되돌림 스크립트 실패**: 처음 돌린 되돌림 스크립트가 vitest의 JSON 결과를 표준 출력에서 읽다가, 다른 출력과 섞여 해석하지 못하고 멈췄다. 바꾼 파일은 스크립트가 `git checkout`으로 되돌렸다. 결과를 파일(`--outputFile`)로 받게 고쳐 다시 돌렸다.
- **R3·R4·R5·R6 되돌림 확인**: 모든 변경을 커밋한 뒤 한 곳씩 바꿔 관련 테스트 파일을 돌리고, 파일을 `git checkout`으로 복구했다(스크립트로 21곳). 바꾼 곳마다 그 동작을 검사하는 테스트가 실패했고, 복구한 뒤 작업 트리에 남은 변경이 없는 것을 확인했다.
  - R3: `EXPIRED` 분기를 빼면 1개(EXPIRED 표시), 화면이 1초마다 시각을 비교해 만료 시각에 버튼을 막게 하면 1개('화면은 시간을 세지 않는다')가 실패했다.
  - R4: `409 HOLD_EXPIRED` 뒤 버튼 막기를 빼면 1개가 실패했다.
  - R5: 응답을 못 받아도 새 키를 만들게 하면 2개(네트워크 오류·502, 10초 시간 초과), 응답을 받아도 같은 키를 쓰게 하면 2개(새 키, 같은 키 뒤 새 키), 요청 중 버튼 막기를 빼면 1개가 실패했다.
  - R6: 결제 화면을 가드 밖에 두면 1개(실제 경로), 선점 조회에 토큰을 붙이지 않으면 33개(MSW 핸들러가 토큰 없는 요청에 401을 줘 화면 테스트가 대부분 실패. 토큰 첨부를 직접 보는 것은 API·화면 각 1개), 해제에 붙이지 않으면 13개, 결제에 붙이지 않으면 20개가 실패했다.
  - 떠날 때의 해제(규칙 밖): `useBlocker`를 끄면 10개, 해제를 `useEffect` 정리 함수로 하면 27개(StrictMode 테스트와, 테스트 끝 정리 때 나간 해제 요청), 결제 중에도 떠나게 하면 1개, 해제를 기다리지 않으면 1개, 로그아웃 확인을 빼면 2개, 토큰이 없어도 해제를 보내면 2개가 실패했다.
  - 넘겨받은 정책: 좌석 선택 화면의 `mounted` 조건을 지우면 2개(Issue가 요구한 '지우면 실패하는 테스트'), 늦게 온 `201`의 해제를 빼면 1개, 로그인 화면의 `mounted` 조건을 지우면 1개, AUTH_REQUIRED 문구 감추기를 빼면 3개(결제·좌석 선택·내 예매), code 없는 502를 다시 `INTERNAL_ERROR`로 하면 7개가 실패했다.
