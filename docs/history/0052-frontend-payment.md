# #52 프론트엔드 결제·예매 확인 화면(R3·R4·R5·R6): 선점 불러오기, 남은 시간, 결제와 멱등 키, 떠날 때 선점 해제

- 기간: 2026-11-27 ~
- Issue: [#52](https://github.com/Rasit-NP/curtain-call/issues/52), PR: (작성 전)
- 관련 결정: [0130](../decisions/0130-frontend-payment-human.md), [0131](../decisions/0131-frontend-payment-recommended.md), [0132](../decisions/0132-frontend-late-responses-and-auth-notice.md), [0133](../decisions/0133-frontend-error-fallback-v2.md)

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 4단계 프론트엔드다. 결제·예매 확인 화면(`/holds/:holdId`)을 만든다.
선점을 불러와 남은 시간을 보여 주고, '결제하기'로 결제하며, 결제가 승인되기 전에 앱 안의 다른 화면으로 가면 선점을 해제한다(명세 1장 5번, 7.3).

좌석 선택 화면(#42)은 선점에 성공하면 `/holds/{id}`로 이동하지만, 그 화면이 없어 라우터 기본 404 화면이 뜬다.
백엔드 선점 조회·해제(#51)는 다른 세션에서 동시에 진행하고, 결제 API는 5단계에서 생긴다. 그래서 세 API는 MSW로 흉내 낸다.
로드맵의 '결제 화면 Issue로' 절에서 넘겨받은 미정 정책 4개(선점 요청 중 좌석 선택 화면을 떠날 때, 로그인 요청 중 떠날 때, 개발 서버의 본문 없는 502, `AUTH_REQUIRED` 문구가 잠깐 보이는 것)도 이 Issue에서 정한다.

## 진행

- 메인 세션이 Issue를 만들고 이 Issue용 워크트리 세션을 시작했다. 워크트리 브랜치는 이미 `origin/main`(`c947d05`)과 같아 맞출 것이 없었고, 이름만 `feat/52-frontend-payment`로 바꿨다.
- 정책 답을 기다리는 사이 #51(PR #53)이 병합됐다. 진행 기록 첫 커밋을 `origin/main`에 rebase하면서 진행 기록 목차의 충돌(#51과 #52 행)을 두 행 모두 남겨 풀었다. PR #53은 명세를 바꾸지 않아 선점 조회·해제 API는 명세 6.5·6.6대로 흉내 낸다.
- Issue의 '아직 정하지 않은 정책' 12개(결제 화면 표시 5, 떠날 때의 해제 3, 로드맵에서 넘겨받은 것 4)와, 명세·Issue를 읽다 찾은 화면 동작 질문을 구현 전에 이 세션에서 사람에게 한 번에 물었다.

## 정책 결정(사람)

구현 전에 15개를 한 번에 물었다. 1~12는 Issue가 '아직 정하지 않은 정책'으로 남긴 것(결제 화면 표시 5, 떠날 때의 해제 3, 로드맵에서 넘겨받은 것 4)이고, 13~15는 명세와 Issue를 읽다 찾은 화면 동작('좌석 다시 선택'을 언제 보일지, `404`·`409` 뒤 결제 버튼, 문구를 지우는 때)이다. 항목마다 선택지·추천·근거를 쓰고, 명세 용어 '안내 문구'는 '화면에 빨간 글씨로 뜨는 알림'이라고 예를 들어 설명했다.

- **첫 답**: 13개는 "추천대로". 두 개는 사람이 자기 말로 답했다.
  - 3번(남은 시간이 0이 되면, 추천은 `EXPIRED`와 같은 화면으로 바꾸고 결제 버튼을 지움): "프론트에서 보여주는 시계가 서버와 동일하란 보장이 없지 않나요? 결제 버튼은 남겨두되, 결제가 불가능하도록 처리합니다. 이 때, 시간이 초과되었다는 메시지를 보여줍니다."
  - 13번('좌석 다시 선택'을 결제 전에 늘 둘지): "'다시 선택'이라고 명시되어 있는 버튼은 없습니다. 결제 화면에서 '뒤로 가기' 혹은 '취소' 형태로 보이게 만듭니다."
- **다시 물은 세 개**: 두 답 때문에 정해지지 않은 점이 생겨 구현하지 않고 다시 물었다.
  - 버튼 이름: '뒤로 가기'(추천)와 '취소' 중 무엇으로 할지. 사람이 '뒤로 가기'를 골랐다.
  - 서버가 만료를 알려 준 경우(들어올 때 `EXPIRED`, 결제 응답 `409`)의 결제 버튼: 3번 답은 화면 시계로 판단한 경우라 이 경우는 정해지지 않았다. 사람은 고르는 대신 "굳이 시계를 보여줘야 하나요? 걍 보여주지 말죠. 제한 시간 안에 결제해야 한다는 문구 정도면 충분하지 않을까요?"라고 답했다.
  - 0초가 됐을 때 시계 줄을 남길지: "화면 시계 걍 빼죠".
- **세 번째로 물은 세 개**: 시계를 빼면 Issue와 명세가 '이미 정한 정책'으로 둔 'R3: 남은 시간이 0이 되면 화면이 버튼을 막는다'가 바뀐다. 그래서 시간이 다 된 것을 누가 판단할지(서버만 / 보이지 않게 셈), 만료가 확인됐을 때 결제 버튼(남기고 막음 / 두지 않음), 시계 대신 둘 문구(시간 없는 문장 / 마감 시각)를 물었다. 사람은 셋 다 추천을 골랐다.
- **기록**: 사람이 자기 말로 정했거나 선택지에서 고른 것(시계 없음과 서버만 판단, 만료 때 버튼을 남기고 막음, 제한 안내 문구, '뒤로 가기')은 [0130](../decisions/0130-frontend-payment-human.md)에 `채택`으로 적었다. "추천대로" 맡긴 것은 결제 화면 [0131](../decisions/0131-frontend-payment-recommended.md), 넘겨받은 정책 [0132](../decisions/0132-frontend-late-responses-and-auth-notice.md)·[0133](../decisions/0133-frontend-error-fallback-v2.md)에 `에이전트 결정`으로 적었다(0045). 0133은 0018을 일부 바꾸므로 0018을 `대체됨(→0133)`으로 바꿨다.
  처음에 "추천대로"였던 2번(남은 시간 형식)과 4번(기준 시계를 응답의 `Date` 헤더로 보정)은 시계를 빼면서 쓸 일이 없어졌다.
- 답은 명세 3.3·7.1·7.2·7.3·7.5·7.6·7.8에 반영했다.
