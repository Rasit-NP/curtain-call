# #39 진행 기록 최신화: 병합된 Issue의 상태와 결과 문장, 대화에서 바로잡은 것

- 기간: 2026-11-27
- Issue: [#39](https://github.com/Rasit-NP/curtain-call/issues/39), PR: [#40](https://github.com/Rasit-NP/curtain-call/pull/40)
- 관련 결정: 없음

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 1·2단계(#27·#28 인증, #35·#36 조회)가 모두 병합됐다. 사람이 "기록을 최신화할 수 있을까요?"라고 물었다.

기록은 두 곳에 있다.
- 로드맵 #13은 GitHub Issue라서 메인 세션이 바로 고쳤다. 끝난 항목을 체크하고 PR 번호를 적었으며, 3·4단계로 넘길 일과 고치지 않은 리뷰 지적을 더했다.
- 저장소의 진행 기록(`docs/history/`)은 PR로만 고칠 수 있어 이 Issue를 만들었다.

진행 기록은 PR 안에서, 병합 전에 쓴다. 그래서 병합된 Issue의 목차 상태가 '진행 중'으로 남았고, '결과' 절에도 '병합 전', '병합을 기다린다' 같은 문장이 남았다.
메인 세션 대화에서 사람이 바로잡은 일 두 가지도 아직 기록에 없었다.

## 진행

- 메인 세션이 Issue와 작업 세션 카드를 만들었다. 사람은 카드에서 "여기에서 진행"을 골랐다.
- 메인 체크아웃은 고치지 않는 규칙(결정 [0027](../decisions/0027-issue-per-worktree-session.md))이라, 메인 세션이 이 Issue용 워크트리를 만들어 그 안에서 고쳤다. 브랜치는 `docs/39-history-sync`다.

## 판단과 근거(에이전트)

- **병합 시점은 날짜 대신 병합 커밋으로 적었다.** GitHub의 병합 시각은 UTC라서, 한국 시간으로는 날짜가 바뀌는 PR이 섞여 있다(예: PR #32는 UTC 11-26, 한국 시간 11-27). 커밋 해시는 이런 모호함이 없다.
- **0062의 상태는 바꾸지 않았다.** 사람이 맡겨 에이전트가 고른 결정이라 `에이전트 결정`이 정확한 표기다([0045](../decisions/0045-decision-status-by-decider.md)). 바로잡은 것은 상태가 아니라 '확인을 다시 묻는' 행동이었다.
- **이미 일어난 판단은 지우지 않았다.** 0036의 '정책 결정(사람)' 절에 있는 "보고에서 확인을 요청한다"는 그때의 판단이라 그대로 두었다. 그 뒤에 일어난 일(다시 물었다가 바로잡음)을 '결과'에 더했다.
- **고친 범위**: 목차 상태 7개, '결과' 절 6개 파일(0027·0028·0029·0033·0035·0036), '기간'의 끝나지 않은 표시(0035·0036), 대화에서 바로잡은 것과 배운 점(0035·0036).

## 결과

PR [#40](https://github.com/Rasit-NP/curtain-call/pull/40)을 만들었고, 사람이 main에 병합했다(병합 커밋 `77e4bdf`).

이 파일의 목차 상태는 PR 안에서 기존 관례대로 '진행 중'으로 두었다. 예상대로 병합 뒤 이 항목도 낡았고, 같은 날 병합된 #41·#42 항목도 '진행 중'으로 남았다.
3단계 뒤 점검에서 이를 찾아 [#46](https://github.com/Rasit-NP/curtain-call/issues/46)에서 '완료'로 고쳤다([0046](0046-payment-lock-order.md)).
병합 전에 쓰는 진행 기록이 병합 뒤에 낡는 구조는 이 Issue 범위 밖이다. 바꿀지는 사람이 따로 정한다.

## 배운 점

- 병합 전에 쓰는 기록에 '병합 전', '기다린다'를 적으면 병합할 때마다 낡는다. 이번처럼 병합 뒤에 따로 고치거나, 처음부터 병합 여부에 기대지 않는 문장으로 써야 한다.
