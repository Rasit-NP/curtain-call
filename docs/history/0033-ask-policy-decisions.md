# #33 정책 결정은 구현 전에 묻고, 결정 상태 '제안'은 실제로 물었을 때만 쓴다

- 기간: 2026-11-27
- Issue: [#33](https://github.com/Rasit-NP/curtain-call/issues/33), PR: [#34](https://github.com/Rasit-NP/curtain-call/pull/34)
- 관련 결정: [0044](../decisions/0044-ask-policy-before-implementing.md), [0045](../decisions/0045-decision-status-by-decider.md)

## 배경

#27·#28(PR #32·#31)에서 세션들이 결정 0031~0043(공개 경로, 오류 `code` 매핑, 계정 시드, 로그인 뒤 이동 등)을 사람에게 묻지 않고 정해 구현했다. 그런 다음 상태를 `제안`으로 적고 PR 본문에 링크만 걸었다. 사람은 결과를 확인하며 이것이 제안이 아니라 통보라고 지적했다. 명세(#3)의 로그인 방식(이메일이 아니라 아이디)도 에이전트가 정했고 따로 확인받지 않았다.

원인은 두 가지였다.

1. 루트 `CLAUDE.md`에는 "규칙이 모호하면 사람에게 넘긴다"만 있어, 무엇이 물어야 할 정책인지를 세션이 판단했다. 세션들은 거의 모든 것을 '명세 안의 세부'로 보고 직접 정했다.
2. `docs/decisions/README.md`가 `제안`을 "PR 병합 전 또는 사람 확인 대기"로 정의했다. 그래서 묻지 않아도 `제안`이 붙고, PR이 병합되면 `채택`이 됐다. 병합이 곧 승인으로 처리됐다.

## 판단과 근거

**사람이 정한 것**

- 2026-11-27 메인 세션(원문): "1, 2, 3 모두 진행하고, 이미 작업이 진행된 결정은 굳이 지금 다시 결정하지 않고 보고만 하세요. 수정이 필요한 부분만 제가 말하겠습니다."
  - 1: 정책 결정은 구현 전에 묻는다([0044](../decisions/0044-ask-policy-before-implementing.md)).
  - 2: `제안`은 실제로 물었을 때만 쓴다. 묻지 않고 에이전트가 정한 것은 상태에 드러나게 한다([0045](../decisions/0045-decision-status-by-decider.md)).
  - 3: 이미 진행된 결정(0031~0043)은 메인 세션이 보고만 했다. 이 Issue에서 다시 정하지 않는다.
- 2026-11-27 이 Issue 세션: Issue가 요구한 대로 새 규칙을 이 작업에도 적용했다. 파일을 고치기 전에 세 가지를 선택지, 추천, 근거와 함께 물었고, 사람이 모두 추천안을 골랐다.
  - 정책 범위 문구: 초안대로. Issue의 네 범주에 '비즈니스 규칙이 모호·필요·충돌할 때'와 '리뷰 지적을 고치다 생긴 정책'을 더하고, 애매하면 정책으로 본다. 'DB 스키마·새 라이브러리 추가도 정책'은 고르지 않았다.
  - 새 상태 이름: `에이전트 결정`. `미확인`, `에이전트 결정(미확인)`은 고르지 않았다.
  - '결정한 사람'만으로 애매한 기존 결정: `에이전트 결정`으로 두고 PR 본문에 목록과 이유를 적는다. 병합과 무응답은 확인이 아니라는 기준을 그대로 따른다.

**에이전트가 정한 것**(내부 구성. 동작이나 규칙의 뜻을 바꾸지 않는다)

- 새 규칙은 '작업 흐름' 아래 '정책 결정' 절에 두고, '비즈니스 규칙' 끝 문단과 '사람에게 넘기는 조건'이 이 절을 가리키게 했다.
- '작업 흐름' 번호를 바꾸지 않으려고 Issue 작성 규칙은 1번에 문장으로 덧붙였다. 'Issue별 세션'이 "위 2번"을 가리키기 때문이다.
- 결정을 두 파일로 나눴다(0044 정책 묻기, 0045 상태 정의). '결정 하나에 파일 하나'를 따랐다.

## 기존 결정의 상태

main에 있던 0001~0043을 각 파일의 '결정한 사람'에 따라 다시 매겼다. 내용은 바꾸지 않았다. PR #31이 이 Issue 전에 병합돼 0040~0043도 포함했다.

- `채택` 11개: 사람이 정한 0003·0004·0005·0007·0008·0010(그대로), 0024·0026~0029(`제안`에서)
- `에이전트 결정` 28개: 에이전트가 혼자 정한 17개(0012~0017·0019~0022·0025·0030·0031·0034·0036·0041·0042)와 애매한 11개(0001·0002·0006·0009·0011·0018·0023·0037·0038·0039·0043)
- `대체됨` 4개: 0032·0033·0035·0040(그대로)

애매한 것의 이유는 [0045](../decisions/0045-decision-status-by-decider.md)의 표에 있다. 묶으면 세 종류다. 사람은 병합만 했다(0001·0002·0009), 일부만 사람이 정했다(0006·0023·0037), 사람은 고치라고만 했고 방식은 에이전트가 정했다(0038·0039·0043). 0011·0018은 Issue로 확인을 요청했지만 답 없이 병합됐다.

## 실패와 수정

- 상태를 일괄로 바꾸는 첫 실행이 아무 파일도 고치지 못했다(`no matches found`). zsh는 따옴표 없는 변수를 단어로 나누지 않아, 번호 목록 전체가 파일 이름 하나로 들어갔다. bash로 다시 실행했다.
- 바꾼 뒤 파일 43개와 목차의 상태를 스크립트로 대조해 모두 같은 것을 확인했다. 하네스의 목차 검사는 링크만 보고 상태는 보지 않는다.
