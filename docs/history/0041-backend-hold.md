# #41 백엔드 선점 생성(R1·R2·R3): 좌석 묶음 선점 API, 동시성, 4석 한도, 지연 만료

- 기간: 2026-11-27
- Issue: [#41](https://github.com/Rasit-NP/curtain-call/issues/41), PR: [#44](https://github.com/Rasit-NP/curtain-call/pull/44)

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 3단계(선점) 백엔드다. 2단계(#35)에서 공연장·공연·좌석 테이블과 공연 상세 API를 만들었고,
이 Issue에서 좌석 묶음 선점 API(`POST /api/holds`)를 만들고 공연 상세의 좌석 상태에 선점 만료를 반영한다.
프론트엔드 좌석 선택 화면(#42)과 동시에 진행한다. 고치는 폴더는 `backend/`와 `docs/`뿐이고, 결정 파일 번호는 0070부터 쓴다(#42는 0080부터).

보안 설정은 #27에서 `/api/holds`를 이미 인증이 필요한 경로로 두었다. 이 Issue는 보안 설정을 고치지 않는다.
선점 조회·해제(4단계)와 결제·예매(5단계)는 만들지 않는다. 그래서 보유 좌석 수(R2)는 이 단계에서 유효한 선점의 좌석만 센다.

## 판단과 근거

사람이 정한 것(2026-11-27, 이 Issue 세션):

- **정수가 아닌 JSON 값**([0072](../decisions/0072-json-numbers-strict.md)): 선점 요청의 `performanceId`·`seatIds`에 소수(`1.5`, `1e3`)나 숫자 문자열(`"1"`)이 오면
  400 INVALID_INPUT이다. Jackson 기본값은 `1.5`를 잘라 `1`로, `"1"`을 `1`로 받아 들인다(스크래치 코드로 Jackson 3.1.8의 동작을 먼저 확인했다).
  결정 0050은 경로의 `1.5`·`1e3`을 400으로 정했으므로, 선택지(소수·문자열 모두 400 / 소수만 400 / 그대로)와 추천(모두 400)을 함께 물었고 사람이 추천을 골랐다.
  전역 Jackson 설정 두 개를 꺼서 이후 결제 요청에도 같이 적용된다. 명세 3.1과 6.4에도 적었다.
- **토큰의 사용자가 DB에 없을 때**([0071](../decisions/0071-missing-token-user-not-handled.md)): 따로 처리하지 않는다. 예상하지 못한 오류로 보고, 외래 키가 막아 500 INTERNAL_ERROR가 된다.
  처음에는 "토큰은 정상인데 그 사용자(sub)가 DB에 없으면 무엇으로 응답할까"라고 묻고 401 AUTH_REQUIRED를 추천했다.
  사람은 "토큰을 DB에서 검증하나요?? 그럼 뭐하러 토큰을 사용하나요?"라고 되물었다.
  질문이 토큰 검증을 DB로 하자는 말처럼 읽혔던 것이다. 실제로는 선점을 만들 때 같은 사용자의 요청을 한 줄로 세우려고 사용자 행을 잠그고(명세 2.4의 예),
  선점에 사용자 id를 외래 키로 저장하므로 그 행이 없을 때의 처리를 정해야 했다. 토큰 검증은 지금처럼 서명·만료만 본다는 것을 먼저 밝히고 다시 물었고,
  사람은 '따로 처리하지 않음'을 골랐다. 401 추천은 '사용자 행이 없다'를 '토큰이 잘못됐다'로 바꿔 읽은 것이라, 토큰을 믿는다는 설계와 어긋났다.

에이전트가 정한 것(Issue 본문 '에이전트가 정하는 것'):

- **스키마**([0070](../decisions/0070-hold-schema.md)): `holds`(저장 상태 ACTIVE·RELEASED·PAID), 선점의 좌석 목록 `hold_seats`, 좌석의 `hold_id`와
  CHECK `(status = 'HELD') = (hold_id IS NOT NULL)`. 좌석 목록과 '좌석을 지금 잡은 선점'을 나눈 것은 결정 0009 때문이다.
  만료 뒤 새 선점이 덮어쓴 좌석도 원래 선점의 목록에는 남아야 선점 조회(4단계)와 결제(5단계)가 묶음을 다룰 수 있다.
  선점 엔티티는 사용자·공연을 id로만 가져 단위 테스트가 바로 만들 수 있게 했다.
- **동시성**([0073](../decisions/0073-hold-concurrency.md)): 사용자 행을 `FOR NO KEY UPDATE`로 잠가 같은 사용자의 요청을 한 줄로 세우고(R2),
  좌석은 한 문장으로 id 오름차순 잠근다(R1). 404 검사와 한도 검사를 좌석 잠금보다 먼저 해서, 오류 순서(404 → 한도 → 좌석)를 지키면서 잠그는 좌석은 4석 이하로 둔다.
  `FOR UPDATE` 대신 `FOR NO KEY UPDATE`를 쓴 이유는 외래 키 확인의 `FOR KEY SHARE`와 부딪히지 않게 하려는 것이다. 결제(5단계)가 같은 사용자의 예매 행을 저장할 때
  선점 요청과 서로 기다리는 일을 미리 피한다. 조건부 UPDATE도 생각했지만 만료 판정을 SQL에 다시 써야 하고, 한도 검사가 먼저라 사용자 직렬화가 어차피 필요했다.
- **유효 판정 한 곳**([0074](../decisions/0074-valid-hold-single-place.md)): '유효한 선점'은 `Hold.isValidAt` 한 곳에 두고, R1 좌석 판정·R2 보유 좌석 수·좌석 API 상태가 모두 이것을 쓴다.
  보유 좌석 수를 SQL 집계로 세면 쿼리는 하나지만 만료 경계가 SQL과 자바 두 곳에 생긴다. 한 곳에 두자 아래 되돌림 5에서 경계를 바꾸었을 때 단위·통합 7개가 함께 실패했다.
  그래서 대응표의 R2 단위 행 '만료·해제된 선점과 다른 공연의 좌석'을 둘로 나눴다. 만료·해제는 단위 테스트가, 다른 공연은 조회 조건이라 통합 테스트가 확인한다.
- **응답 정렬**: 선점 응답의 좌석은 잠근 좌석을 자바에서 row·number 순으로 정렬한다. `String.compareTo`는 UTF-16 단위로 비교해 보충 문자에서 명세 5의
  '코드 포인트 순서'와 달라지므로, 코드 포인트로 비교하는 `SeatOrder`를 두고 단위 테스트로 차이를 보였다.
- **테스트 방법**: 동시성 테스트는 `CountDownLatch`로 스레드를 동시에 출발시키고 응답(상태·code)과 DB 최종 상태(선점 행, 좌석의 저장 상태·holdId, 선점의 좌석 목록)를 함께 본다.
  두 요청이 부딪히는 경우는 경합이 한 번에 일어나지 않을 수 있어 공연을 새로 만들어 반복한다(교착 상태 50회, 겹치는 묶음·같은 사용자 20회).
  실패한 요청은 모두 "어떤 좌석도 선점되지 않았음"을 DB에서 확인한다. 404 테스트처럼 구현 전에도 404로 통과해 버리는 테스트는 끝에 "그 좌석을 빼면 선점된다"를 더해,
  구현 전에는 실패하고 404가 경로가 아니라 좌석 때문인 것을 보이게 했다.
- 2단계의 저장 상태 테스트(holdId 없이 HELD를 만듦)는 지우지 않고, 실제 선점으로 HELD를 만드는 R3 테스트('공연 상세는 만료 시각 1초 전까지 HELD, 만료 시각부터 AVAILABLE')로
  바꿨다(PR #37 리뷰 지적 3). AVAILABLE·SOLD가 그대로 나오는 확인은 남겼다.

## 실패와 수정

- **좌석 id가 아주 많으면 500**: 404 검사를 `count ... where s.id in :ids`(JPQL)로 처음 구현했다. 선점 요청의 좌석 수 상한은 400이 아니라 409(명세 6.4)라
  좌석 id 개수에 상한이 없다. 그래서 구현 전에 '7만 개' 테스트를 써 두었고, 이 테스트가 500으로 실패했다.
  로그는 `PreparedStatement는 최대 65,535 개의 매개 변수를 가질 수 있습니다`(PostgreSQL JDBC 드라이버)였다. `IN`이 좌석 id마다 매개변수를 만든 것이다.
  배열 매개변수 하나(`id = ANY(?)`, 네이티브 쿼리)로 바꿔 통과했다. 좌석을 잠그는 조회는 한도 검사 뒤라 4석 이하이므로 그대로 `IN`을 쓴다.

## 규칙 테스트 되돌림 확인

구현의 해당 부분을 잠시 되돌리고 단위 테스트 전체와 선점 관련 통합 테스트(137개)를 돌린 뒤, `git checkout`으로 복구했다. 되돌리지 않은 기준 실행은 137개 모두 통과였다.

| 되돌린 것 | 실패한 테스트 |
|---|---|
| 1. 좌석 잠금 제거(`@Lock` 삭제) | R1 동시성 3개: 같은 좌석 10개(201이 5개), 겹치는 묶음(둘 다 201), 반대 순서 묶음(둘 다 201) |
| 2a. 좌석 잠금 문장의 `order by id`만 제거 | 없음. 한 문장으로 잠그면 두 요청이 같은 실행 계획으로 같은 순서로 잠근다(아래) |
| 2b. 좌석을 요청 순서대로 한 좌석씩 잠금 | R1 '반대 순서 묶음 50회'가 1회째에 `[201, 500]`. 로그에 PostgreSQL `deadlock detected` → `CannotAcquireLockException` |
| 3. 사용자 행 잠금 제거 | R2 '같은 사용자 3석 묶음 두 개 동시'가 1회째에 `[201, 201]`(6석) |
| 4a. 서비스의 한도 검사 제거 | R2 4개: 5석 묶음(도메인의 1~4석 검사에 걸려 500), 4석 만료 1초 전(201), 오류 순서(SEAT_ALREADY_HELD), 같은 사용자 동시 |
| 4b. 한도 경계를 4석에서 5석으로 | R2 4개: 단위 '보유 3석이면 1석은 허용하고 2석은 거부', 5석 묶음, 4석 만료 1초 전, 오류 순서. 같은 사용자 동시(3+3=6)는 통과 |
| 5. 만료 경계(만료 시각과 같은 순간도 유효) | 7개: 단위 R3 경계, R1 판정, R3 API 상태, R2 만료·해제, 통합 R3 같은 순간, R3 공연 상세, R2 4석 만료 순간 |
| 6. 좌석 판정(409 SEAT_ALREADY_HELD) 제거 | 6개: R1 묶음 중 한 좌석, R1 판매·내 선점, R3 1초 전, R1 동시성 3개 |
| 7. 보유 좌석 수를 모든 공연에서 셈 | R2 '다른 공연' 테스트, 그리고 반복마다 공연을 바꿔 같은 사용자를 쓰는 동시성 테스트 3개 |
| 8. 토큰의 사용자 대신 고정 id(0)로 선점 | R6 2개(유효한 토큰, 로그인 흐름). 선점을 만드는 다른 테스트 18개도 함께 실패 |
| 9. 공연 상세의 좌석 상태를 저장 상태로 | R3 '공연 상세는 만료 시각 1초 전까지 HELD, 만료 시각부터 AVAILABLE' |
| 10. Jackson 숫자 설정 제거(결정 0072, 규칙 테스트는 아님) | 400 테스트 5개(소수, 지수 표기, 숫자 문자열 두 개, 소수점이 있는 수)가 201 |

2a는 가설을 세우고 확인한 것이다. `IN (a1, a2)`와 `IN (a2, a1)`은 같은 실행 계획(인덱스의 정렬된 키나 같은 물리 순서)으로 읽혀 같은 순서로 잠긴다.
그래서 이 구현에서는 정렬을 빼도 교착 상태가 생기지 않고, 교착 상태 테스트가 잡는 것은 2b처럼 요청 순서대로 한 좌석씩 잠그는 구현이다.
실행 계획이 다른 경우까지 막으려고 명세 2.4대로 정렬은 둔다. 대응표 R1의 설명에도 적었다.

R6는 보안 설정(#27)을 되돌리지 않았다. 이 Issue는 보안 설정을 고치지 않고, 토큰이 없을 때의 401은 #27에서 되돌림 확인을 했다.
이 Issue의 R6 테스트가 지키는 것은 '토큰의 사용자가 선점의 주인이 된다'이므로 8번처럼 확인했다.

## 배운 점

- 정책 질문은 '무엇이 왜 필요한지'를 먼저 적어야 한다. "토큰은 정상인데 사용자가 없으면"으로 시작한 질문은 토큰 검증 방식을 묻는 것으로 읽혔다.
  추천(401)도 결국 '사용자 행이 없다'를 '토큰이 잘못됐다'로 바꿔 읽은 것이어서, 다시 설명하자 사람이 바로 '따로 처리하지 않음'을 골랐다.
- 동시성 테스트의 되돌림 확인은 '무엇을 되돌리느냐'에 따라 결과가 다르다. 한 문장 잠금에서 정렬만 빼서는 교착 상태가 생기지 않았다. 테스트가 약한 것이 아니라
  잠그는 방식이 순서를 이미 고정하고 있었다. 되돌림은 그 테스트가 막으려는 실제 실수(요청 순서대로 한 좌석씩 잠금)로 해야 의미가 있다.
- 상한이 없는 입력 목록을 SQL `IN`으로 넘기면 드라이버 상한에서 500이 된다. 명세가 상한을 400이 아니라 다른 오류(409)로 정했을 때 생기는 틈이라, 구현 전에 테스트를 써 둔 것이 잡았다.
