# #36 프론트엔드 조회 화면(R6): 공연 목록, 내 예매, 공통 헤더와 로그아웃

- 기간: 2026-11-27
- Issue: [#36](https://github.com/Rasit-NP/curtain-call/issues/36), PR: [#38](https://github.com/Rasit-NP/curtain-call/pull/38)
- 관련 결정: [0060](../decisions/0060-frontend-query-screens.md), [0061](../decisions/0061-frontend-header-login-logout.md), [0062](../decisions/0062-frontend-load-status-role.md), [0063](../decisions/0063-frontend-header-token-subscription.md), [0064](../decisions/0064-frontend-date-format-intl.md), [0065](../decisions/0065-frontend-load-hook-and-screen-tests.md)

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 2단계(조회) 프론트엔드다. 공연 목록 화면(`/`), 내 예매 화면(`/reservations`), 모든 화면 위의 공통 헤더와 로그아웃을 만든다.
1단계(#28)의 로그인 화면, 인증 가드, `401 AUTH_REQUIRED` 공통 처리를 그대로 쓴다. 백엔드 조회(#35)와 동시에 진행하고, API는 MSW로 흉내 낸다. 내 예매 API는 백엔드 5단계에서 생긴다.

## 정책 결정(사람)

- **Issue의 '이미 정한 정책'**([0060](../decisions/0060-frontend-query-screens.md)): 메인 세션 대화에서 사람이 정했다. 두 화면의 표시 항목, 일시·가격 형식, 빈 목록·로딩 문구, 항목 전체 링크, 헤더 구성, 로그아웃 동작이다.
- **구현 전에 물은 세 가지**([0061](../decisions/0061-frontend-header-login-logout.md)): Issue가 '아직 정하지 않은 정책'으로 남긴 것을 구현 전에 이 세션에서 선택지·추천·근거와 함께 한 번에 물었다. 사람은 세 가지 모두 추천을 골랐다.
  - 헤더 '로그인'으로 로그인한 뒤: 보던 화면으로 돌아간다. 지금은 로그인 전에 헤더가 보이는 화면이 공연 목록과 로그인 화면뿐이라 공연 목록으로 보내는 것과 차이가 작다는 점도 함께 알렸다.
  - 로그인 화면에도 헤더를 보여 주고, '로그인' 링크는 지금 화면으로 표시하되 눌러도 돌아갈 곳을 잃지 않게 한다.
  - 로그아웃 뒤 안내 문구는 보여 주지 않는다.
- **구현하며 찾은 모호함**([0062](../decisions/0062-frontend-load-status-role.md)): Issue의 "안내 문구는 `role="alert"` 영역에 둔다"가 로딩·빈 목록 문구까지 뜻하는지 모호해 같은 질문에 넣어 물었다. 사람은 "잘 모르겠음. 중요한 내용이 아니면 추천대로 진행/중요한 내용이면 자세한 설명을 부탁함"이라고 답했다. 보이는 글과 흐름은 같고 화면 읽기 프로그램이 읽는 방식과 테스트가 찾는 역할만 다르며, 나중에 몇 줄로 바꿀 수 있어 중요하지 않다고 보고 추천(로딩·빈 목록은 `role="status"`, 오류만 `role="alert"`)대로 했다. 사람이 그 내용을 확인한 것은 아니라 `에이전트 결정`으로 기록하고 보고에서 확인을 요청한다.

## 구현 중 판단과 근거(에이전트)

- **API 함수와 응답 타입**: `src/api/types.ts`에 명세 5장의 `PerformanceSummary`, `SeatRef`, `Reservation`을 두고, `getPerformances`(`auth: false`)와 `getMyReservations`(`auth: true`)를 만들었다. 공개 API에 토큰을 붙이지 않는 것은 R6 테스트로 지킨다.
- **헤더의 로그인 상태는 토큰 저장소의 변경 알림으로**([0063](../decisions/0063-frontend-header-token-subscription.md)): 토큰은 로그인 화면, 헤더, API 클라이언트 세 곳에서 바뀐다. 저장소가 알리고 헤더가 `useSyncExternalStore`로 읽게 했다. 화면 이동이 있으면 헤더도 다시 그려져 알림 없이도 대부분 맞게 보이지만, 로그인 화면에서 늦게 온 `AUTH_REQUIRED`처럼 이동 없이 토큰만 지워지는 경우가 있다. 이 경우를 테스트로 만들어, 알림을 빼면 그 테스트만 실패하는 것을 확인했다.
- **일시 형식**([0064](../decisions/0064-frontend-date-format-intl.md)): `Intl.DateTimeFormat`에 `Asia/Seoul`을 주고 부분만 받아 이어 붙였다. 런타임마다 다를 수 있는 기본 형식 문자열에 기대지 않는다. 날짜가 바뀌는 경계(UTC 15:00)와 해가 바뀌는 경계를 테스트했다.
- **화면 불러오기 공통 훅**([0065](../decisions/0065-frontend-load-hook-and-screen-tests.md)): 두 화면의 로딩·오류 처리가 같아 `useLoad`와 `LoadStatus`로 묶었다. `AUTH_REQUIRED`도 다른 오류처럼 `code`로 받을 뿐이고, 로그인 이동은 공통 처리(0043)가 한다.
- **테스트 도우미**: API별 MSW 핸들러(`src/test/handlers.ts`)와 응답 객체 생성 함수(`src/test/data.ts`)를 만들었다. 내 예매 핸들러는 서버처럼 토큰이 없으면 `401 AUTH_REQUIRED`를 준다. 기본 핸들러는 여전히 두지 않는다(0025).
- **좌석 선택 화면 링크**: 화면은 3단계에서 만든다. 이 Issue는 항목 링크의 주소(`/performances/{id}`)와 누르면 그 경로로 가는 것까지 확인한다.
- **새 라이브러리 없음**.

## 실패와 수정

- **테스트를 먼저 쓰고 실패 확인**: API 함수·형식 함수 테스트(모듈 없음), 토큰 변경 알림 테스트(함수 없음), 세 화면 테스트 27개(화면 없음)가 실패하는 것을 확인한 뒤 구현했다.
- **기존 테스트 4개가 핸들러 없는 요청으로 실패**: `/`가 빈 화면에서 공연 목록 화면으로 바뀌어, 로그인 뒤 `/`로 가는 기존 테스트(로그인 화면 2개, 가드 1개, 라우터 1개)가 공연 목록 요청을 보냈다. 테스트가 핸들러 없는 요청을 실패로 만드는 설정(0025)이 잡았다. 각 테스트에 공연 목록 핸들러를 더했다. 기대값은 바꾸지 않았다.
- **빈 목록 테스트가 로딩 문구를 잡음**: 빈 목록 문구와 로딩 문구가 모두 `role="status"`라, `findByRole('status')`가 먼저 보이는 로딩 문구를 잡았다. 문구가 바뀔 때까지 기다리게 고쳤다.
- **R6 되돌림 확인 중 불안정한 테스트 발견**: 공연 목록 함수를 `auth: true`로 바꿨을 때 관계없는 내 예매 테스트도 실패했다. 원래 코드로 전체 테스트를 되풀이하자 가끔 실패해 불안정한 테스트였다. 실패 화면을 보니 라우터 위치는 `/login`인데 DOM은 아직 내 예매 화면이었다. React Router가 화면 이동을 transition으로 그려 DOM이 늦게 바뀌는데, 내 예매 화면도 받은 오류의 문구('로그인이 필요합니다.')를 잠깐 보여 줘서 테스트가 그것을 잡고 바로 로그인 입력을 찾았다. 이어서 전체 실행 15번 중 3번, 기존 로그인 화면 테스트('로그인에 성공하면 … 공연 목록(/)으로 간다')가 같은 이유로 실패했다. 위치(`/`)만 기다리고 로그인 버튼이 사라졌는지 검사했는데, `/`가 그릴 것이 있는 화면이 되면서 드러났다. 그려진 화면의 요소를 `findBy…`로 기다리게 고친 뒤 전체 실행 30번 모두 통과했다([0065](../decisions/0065-frontend-load-hook-and-screen-tests.md)).
- **R6 되돌림 확인**: 내 예매를 가드에서 빼면 R6 테스트 3개(직접 들어감, 헤더의 내 예매, 로그인 화면의 헤더)가, 공연 목록 함수를 `auth: true`로 바꾸면 R6 테스트 2개(API 함수, 화면)와 내 예매 `AUTH_REQUIRED` 테스트가 실패했다. 헤더도 되돌려 보았다: 로그인 링크에 돌아갈 곳을 넘기지 않으면 2개, 로그인 화면에서도 지금 경로를 넘기면 1개, 토큰 변경 알림을 빼면 2개, 로그아웃이 토큰을 지우지 않으면 2개가 실패했다. 모두 원래대로 복구했다. 이번에는 모든 변경을 먼저 커밋한 뒤 되돌려, #28 때처럼 커밋하지 않은 작업이 지워질 위험이 없었다.

## 배운 점

- 화면 이동 뒤의 DOM을 검사하는 테스트는 라우터 상태가 아니라 그려진 화면을 기다려야 한다. 라우터 상태와 DOM은 transition 동안 어긋난다. 이전 화면이 가볍게 그려질 때는 드러나지 않다가, 그 화면이 무거워지면 가끔 실패한다.
- 되돌림 확인은 테스트를 여러 번 돌려 보는 기회이기도 하다. 관계없는 테스트가 실패하면 되돌린 것과 무관한 불안정함을 의심한다.
- 상태를 `에이전트 결정`으로 정확히 적는 것과 사람에게 확인을 다시 요청하는 것은 다르다. 사람이 맡긴 결정은 끝났고, 세션 보고를 사람에게 옮기는 메인 세션도 이미 답한 것은 걸러야 한다.
