## 배경

로드맵 1(MVP, R1~R6) [#13](https://github.com/Rasit-NP/curtain-call/issues/13)을 마치고 닫았다. 2026-11-28 메인 세션에서 사람이 로드맵 2 [#64](https://github.com/Rasit-NP/curtain-call/issues/64)를 승인했다.
회원가입(필수)과 UI 다듬기, 예매 취소, 좌석 실시간 반영(SSE), 뮤테이션 테스트(PIT), k6 부하 테스트, GitHub Actions 도입, 먼저 배포. 대기열과 공연 등록은 만들지 않는다.

지금 문서는 그 결정과 네 군데에서 어긋난다.

1. 루트 `CLAUDE.md` '금지 사항'과 명세 8장이 회원가입을 범위 밖에 둔다. 명세 2.1도 "회원가입은 없고 시드로만 만든다"고 한다.
2. 루트 `CLAUDE.md` 'Issue 등록 범위'가 닫힌 #13을 로드맵으로 가리킨다.
3. 사람이 "이슈를 등록하기 전에는 반드시 저의 승인을 거친 후 등록하도록 하세요"라고 했다(원문). 이 규칙은 메인 세션의 메모리에만 있어 다른 세션은 모른다.
4. '사람에게 넘기는 조건'에 'CI·배포 설정을 바꿔야 한다'가 있어, 이 문구대로면 1·2단계 CI·배포 Issue 세션은 시작하자마자 멈춰야 한다.

이 Issue는 문서만 고친다. 1단계 Issue 세션이 새 규칙을 읽도록, 1단계 Issue는 이 PR이 병합된 뒤 등록한다.

## 정책 결정(사람)

Issue의 '아직 정하지 않은 정책' 1번을 이 세션에서 선택지·추천·근거와 함께, 바뀐 문구를 미리 보여 주며 물었다.

- **질문**: '사람에게 넘기는 조건'의 '인증·보안을 바꿔야 한다'를 CI·배포처럼 'Issue 범위 안에서는 고친다'로 바꿀지.
  지금 문구대로면 3단계 회원가입 Issue 세션은 인증을 바꾸므로 시작하자마자 멈춰야 한다. 1단계 인증 Issue #27은 같은 문구 아래에서 Issue 범위로 보고 진행했다.
- **선택지**: (1) 로드맵 Issue 범위 안에서는 고친다(추천), (2) 지금 문구 유지(항상 넘김), (3) 회원가입 Issue만 예외.
- **추천 근거**: #27을 진행한 방식과 같다. 계정·비밀번호·인증·보안은 이미 '정책 결정'이라 구현 전에 물으므로 결정은 여전히 사람이 한다. CI·배포와 같은 문구로 두면 세션이 두 조건을 다르게 읽지 않는다.
  (3)은 2단계 'E2E 초기화 API를 운영에서 닫기'나 6단계 SSE의 로그인 필요 여부 같은 다른 단계의 보안 항목에서 다시 멈춘다.
- **답**: (1). 미리 보인 문구 그대로 반영했다. 인증·보안과 CI·배포를 한 항목으로 묶고, 단서는 "로드맵에 있는 Issue는 그 Issue가 범위로 다루는 인증·보안, CI·배포 설정을 그 Issue 범위 안에서 고친다. 정책은 '정책 결정'대로 구현 전에 묻는다"이다.
  처음에 CI·배포만 따로 나눠 둔 문구('비밀값… 로드맵에 있는 CI·배포 Issue에서도 이 일은 넘긴다' 포함)는 이 문구로 바꿨다. 비밀값·외부 계정 항목은 단서가 붙지 않아 로드맵 Issue에도 그대로 적용된다.
- 결정 [0186](../decisions/0186-handoff-roadmap-issue-scope.md)(`채택`)에 남겼다.

## 판단과 근거(에이전트)

Issue가 에이전트에게 맡긴 것(문구와 위치, 결정 파일 나누기, 0026 대체 여부, 결정 번호)이다.

- **결정 번호 0180~0186**: main의 마지막은 0163이고, 0170~0179는 #60 브랜치가 쓴다. 지금까지 세션마다 10번 단위로 시작한 관례(#59는 0160, #60은 0170)를 따랐다.
- **결정을 7개로 나눴다**: #64 0단계가 적은 결정 기록(범위 변경, 대기열·공연 등록 제외, GitHub Actions 도입, 배포 먼저, 로드맵 전환)에 이 Issue의 두 규칙(Issue 등록 승인, 넘기는 조건)을 더했다. 결정 하나에 파일 하나 규칙을 따랐다.
  '범위 변경'은 회원가입을 넣는 것(0181)과 공연 등록을 빼는 것(0182)으로 나눴다. 0182는 대기열과 공연 등록의 근거가 같은 꼴이라 한 결정에 두었다.
- **0026은 보완이 아니라 대체(0185)**: 0026의 결정과 '적용과 남은 점'이 닫힌 #13을 직접 가리킨다. 보완만 하면 목차에서 #13을 가리키는 결정이 `채택`으로 남는다.
  저장소 규칙도 결정이 바뀌면 원래 파일을 고치지 않고 새 파일을 만든다. 0026의 근거(Issue 13개를 만든 일)는 0026 파일에 그대로 남는다.
- **'Issue 등록 범위' 절 제목은 그대로 두었다**: 승인 규칙이 범위 규칙은 아니지만, 0026·Issue 본문 등 여러 곳이 이 제목으로 가리킨다.
- **명세 8장**: 예매 취소를 '규칙에 없어 두지 않는 것'에서 꺼내 '로드맵 2의 5단계에서 사람이 정한다'로 따로 적었다. 대기열·공연 등록의 근거는 8장에 두고, 루트 `CLAUDE.md`는 8장을 가리키게 했다(근거를 두 곳에 쓰지 않으려고).
  회원가입이 범위 안으로 들어왔다는 것도 8장에 한 줄 남겼다. 8장을 보고 '회원가입이 왜 목록에서 빠졌나'를 찾는 사람을 위해서다.
- **명세 2.1의 예매 행 '취소 기능은 없다'는 고치지 않았다**: 지금도 사실이고, Issue가 2.1은 사용자 행만 고치라고 했다. 5단계 명세 Issue에서 고친다.
- **근거를 지어내지 않았다**: 메인 세션의 대화 원문이 이 세션에 없어, 결정의 근거는 #64·#65 본문에 적힌 것만 썼다. 0182·0184의 '고려했지만 고르지 않은 것'은 에이전트가 정리했다고 표시했다.
