## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 5단계(결제) 첫 번째 백엔드다. 결제 API(`POST /api/payments`)와 내 예매 API(`GET /api/reservations`)를 만든다.
결제가 승인되면 선점은 `PAID`, 좌석은 `SOLD`가 되고 예매가 생긴다. 프론트엔드 결제 화면(#52)과 내 예매 화면(#36)은 이 두 API를 MSW로 흉내 내며 이미 끝났다.
멱등 기록(같은 키의 결과 저장·재사용, 같은 키 동시 요청)은 다음 Issue #56이 하고, 이 Issue는 `Idempotency-Key` 헤더의 검증까지만 한다.
이 세션은 `backend/`와 `docs/`만 고치고, 결정 번호는 0140부터 쓴다.

## 판단과 근거

사람이 정한 것(2026-11-28, 이 세션에서 선택지·추천·근거를 함께 물음. [0141](../decisions/0141-idempotency-key-format.md), `채택`):

- `Idempotency-Key`의 '공백뿐'과 '100자'를 판단하는 방법(Issue의 '아직 정하지 않은 정책'): **ASCII 출력 문자(0x21~0x7E) 1~100자만 받는다**(추천안).
  공백·탭·제어 문자·ASCII가 아닌 문자가 하나라도 있으면 400이라 '공백뿐'도 여기에 걸리고, 글자 수는 문자 수 = 바이트 수다.
  고르지 않은 것: 명세 문구 그대로(앞뒤 공백만 지우고 ASCII 밖 문자 허용), 유니코드 공백까지 공백으로.
- 명세를 읽다 찾은 정책: `Idempotency-Key` 헤더가 두 번 이상 오면? **400 INVALID_INPUT**(추천안). 고르지 않은 것: 첫 번째 값을 씀.

에이전트가 정한 것(Issue 본문 '에이전트가 정하는 것', 모두 `에이전트 결정`):

- **스키마**([0140](../decisions/0140-reservation-payment-schema.md)): `reservations`(`hold_id` 유니크), `reservation_seats`(`seat_id` 유니크: 취소가 없어 한 좌석은 예매 하나),
  `payments`(SUCCEEDED일 때만 `reservation_id`). 잠금이 막는 일을 DB가 한 번 더 막는다. 예매 시각은 모든 잠금 뒤에 읽은 판정 시각이다.
- **결제 흐름과 트랜잭션 경계**([0142](../decisions/0142-payment-impl.md)): 사용자 행 → (멱등 기록 자리, #56) → 선점 행 → 좌석(id 오름차순)을 잠그고, 현재 시각을 읽어 판정한다(결정 0100 그대로).
  서비스는 404·409·402를 예외가 아니라 결과 값(`PaymentOutcome`)으로 돌려주고 커밋한다. 그래서 거절(402)의 결제 FAILED가 남고, #56은 같은 트랜잭션에서 그 결과를 저장하면 된다.
- **도메인**: `Hold.pay(판정 시각)`은 판정 시각에 유효해야 PAID로 바꾼다(서비스의 만료 판정이 빠져도 만료된 선점이 팔리지 않게). `Seat.sell(holdId)`는 그 선점이 잡은 HELD 좌석만 판다.
  #51의 `HoldService.isOpenHoldOf`를 `Hold.isOpenFor`로 옮겨 조회·해제·결제가 함께 쓴다. 보유 좌석 수는 `HoldLimit.ownedSeatCount`(유효한 선점 + 예매 좌석)다.
- **모의 결제**: `FakePaymentGateway` 하나를 모든 프로필에서 쓰고, 테스트 조작(다음 호출 거절, 호출 횟수, 멈추기, 초기화)을 같은 클래스에 둔다. 통합 테스트 기반이 매 테스트 전에 초기화한다.
- **동시성 테스트 방법**([0143](../decisions/0143-payment-concurrency-test-latch.md)): 모의 결제를 멈춰 결제가 잠금을 쥔 채 판정을 통과한 상태를 만들고, 나중 요청이 DB 행 잠금을 기다리는 것을
  `pg_stat_activity`로 확인한 뒤 푼다. #51에서 경합 테스트가 한 순서만 만들어 되돌림을 놓친 것(결정 0121)을 다시 겪지 않으려고, 시간에 기대지 않고 순서를 만든다.
  교착 상태 테스트만 순서를 정하지 않고 결제를 0~10ms 늦게 보낸다(0121과 같은 방법).

## 실패와 수정

- **`Idempotency-Key`에 제어 문자가 있으면 500.** 새로 쓴 통합 테스트의 'DEL 문자가 든 키 → 400' 매개변수 하나가 500으로 실패했다.
  - 로그: Spring Security `RequestRejectedException`(`StrictHttpFirewall`이 헤더 값을 거부). 원인 가설: 방화벽은 헤더 값을 요청 처음이 아니라 '읽는 순간' 검사하므로,
    컨트롤러가 이 헤더를 읽을 때 예외가 나고, 공통 처리기는 그것을 예상하지 못한 예외(500)로 본다.
  - 실제 서버에서는 어떤지 임시 테스트(실제 Tomcat, 소켓으로 바이트를 보냄, 확인 뒤 지움)로 확인했다. DEL·0x01은 Tomcat이 먼저 400으로 막는다. 그런데 한글 키를 UTF-8로 보내면
    Tomcat이 ISO-8859-1로 읽어 C1 제어 문자(U+0082)가 든 문자열이 되고, 방화벽이 거부해 **500**이었다. 사람이 정한 'ASCII 밖 문자는 400'(결정 0141)과 어긋나는 결함이다.
    앱이 읽지 않는 헤더(`X-Note: 키`)는 영향이 없어(200) 가설과 맞았다.
  - 수정: 이 헤더를 읽다 난 방화벽 거부만 400 INVALID_INPUT으로 바꾼다(`IdempotencyKeyHeader.read`). 보안 설정은 바꾸지 않았다. 서버가 읽은 모양의 한글 키 문자열을
    통합 테스트 매개변수에 더해, 고치기 전에 실패하는 것(500)을 확인한 뒤 고쳤다(1회 시도로 고침).
- **확인하지 않은 효과를 결정에 적었다.** 결정 0140의 근거에 '잠금을 빼면 나중 결제가 유니크 제약이나 `Seat.sell` 확인에 걸려 500으로 끝난다'고 먼저 적었다.
  실제로 결제의 사용자 행·선점 행 잠금을 함께 빼 보니, 같은 선점의 두 번째 결제는 `Seat.sell` 확인(이미 SOLD)에 걸려 500이었고 유니크 제약까지는 가지 않았다(1회 실행).
  결정 문구를 그대로 고치고, 제약 자체는 스키마 테스트로 따로 확인했다. 교착 상태 되돌림의 원인(`deadlock detected`)도 같은 이유로 로그를 다시 확인한 뒤 적었다.

## 규칙 테스트 되돌림 확인

운영 코드의 한 부분을 잠시 바꾸고 해당 테스트를 돌린 뒤 git으로 되돌렸다. 매번 `git diff`로 운영 코드가 커밋과 같은지 확인했다. 실행 횟수를 적지 않은 것은 1회 실행이다.

| 현재 시각을 잠그기 전에 읽음 | R4 '잠금을 기다리는 동안 만료 시각이 지나면 409'(사용자 행을 기다린 뒤 201). 1개 |
| 선점 행 잠금 → 일반 조회 | '같은 선점에 결제와 해제가 동시에 오면…'(승인 뒤 해제가 404 대신 500). 1개 |

| `HoldLimit.ownedSeatCount`가 예매 좌석을 더하지 않음 | 단위 R2 2개, 통합 R2 '예매 2석'. 3개 |

## 배운 점

- 프레임워크가 요청 값을 '처음'이 아니라 '읽는 순간' 검사하면, 그 검사의 예외가 컨트롤러 안에서 나 예상하지 못한 오류(500)가 된다. 입력 검증 테스트에는 MockMvc가 넘기는 자바 문자열만이 아니라
  실제 서버가 바이트를 읽은 모양(헤더는 ISO-8859-1)도 넣는다.
- 결정 기록의 '근거'에 되돌림 결과를 적을 때는 실제로 돌려 본 것만 적는다. 짐작한 결과(유니크 제약이 막는다)와 실제 결과(그 앞의 도메인 확인이 막는다)가 달랐다.
