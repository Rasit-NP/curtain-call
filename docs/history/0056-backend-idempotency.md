## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 5단계(결제) 두 번째 백엔드다. 결제 요청의 멱등 키(R5)를 만든다.
같은 사용자가 같은 `Idempotency-Key`로 결제를 다시 보내면 다시 처리하지 않고 처음 결과를 그대로 돌려주고, 같은 키 요청이 동시에 와도 예매는 하나만 생기게 한다.
프론트엔드 결제 화면(#52)은 응답을 받지 못했을 때 같은 키로 다시 보내며 이미 끝났다. 바로 앞 #55(PR #57)가 결제 API와 키 헤더 검증(결정 0141)을 만들고,
결제 흐름의 사용자 행 잠금 뒤·선점 행 잠금 앞에 멱등 기록이 들어갈 자리를 남겼다. 이 세션은 `backend/`와 `docs/`만 고치고, 결정 번호는 0150부터 쓴다.

## 판단과 근거

사람에게 물은 정책은 없다. 묻지 않은 근거:

- '저장한 응답을 그대로'가 무엇까지인지: 명세 6.7.1이 "응답(상태 코드와 본문)을 저장한다", "저장한 응답을 그대로 돌려준다"고 정했다. 상태 코드와 본문을 처음과 같게 돌려주고,
  재요청임을 알리는 헤더 같은 것은 더하지 않는다(더하면 API 계약을 바꾸는 정책이다). 테스트는 상태·Content-Type·본문 문자열이 같은지 본다.
- 토큰의 사용자가 DB에 없을 때: 멱등 기록이 사용자를 외래 키로 저장해 결제가 404에서 500으로 바뀐다. 결정 0071(사람이 정함)이 "따로 처리하지 않고 외래 키가 막아 500",
  "결제(5단계)도 … 이 결정을 따른다"고 정해 두었으므로 새 정책이 아니다. 테스트로 고정하고 결정 0150에 적었다.
- 같은 키·다른 선점 400의 detail 문구: 클라이언트는 code만 보고 detail은 화면에 쓰지 않는다(spec 3.1, 7.6). 이전 Issue들처럼 에이전트가 정했다.

에이전트가 정한 것(Issue 본문 '에이전트가 정하는 것', 모두 `에이전트 결정`):

- **테이블과 저장 형식**([0150](../decisions/0150-idempotency-record-schema.md)): `idempotency_records`에 (사용자, 키) 유니크, 응답 상태와 본문, 상태는 201·402·404·409만(CHECK).
  없는 선점의 404도 저장해야 하므로 `hold_id`에는 외래 키를 두지 않는다. 201은 응답 본문 JSON을 그대로, 오류는 code·detail만 저장해 공통 처리기가 오류 본문을 다시 만든다
  (오류 본문을 만드는 곳을 늘리지 않는다는 `backend/CLAUDE.md` 규칙).
- **처리 방법**([0151](../decisions/0151-idempotency-impl.md)): 사용자 행을 잠근 바로 뒤에 `INSERT … ON CONFLICT DO NOTHING`으로 키를 먼저 잡는다. 같은 키 요청은 유니크 제약에서
  먼저 요청이 끝나기를 기다리고, 먼저 요청이 커밋했으면 그 응답을, 500으로 되돌려졌으면 처음처럼 처리한다. 명세 2.4의 잠금 순서(사용자 행 → 같은 키의 멱등 기록 → 선점 행 → 좌석)를 그대로 만든 것이다.
  결과는 같은 트랜잭션에서 기록에 채운다. 응답 모양은 API 계층이 함수로 넘기고, 처음 응답도 저장한 값으로 만들어 처음 응답과 재요청 응답이 같은 경로를 지나게 했다.
- **테스트 방법**([0152](../decisions/0152-idempotency-test.md)): 같은 키 재요청은 다시 처리해도 같은 응답이 나올 수 있으므로(#51의 결정 0121과 같은 함정), 다시 처리하면 결과가 달라지는
  상황(결제·해제·만료, 없던 선점 id가 생김, 거절 지정이 없음)을 만든 뒤 보낸다. 같은 키 동시 요청은 결정 0143의 래치와 `pg_stat_activity` 방법을 쓴다. 500은 모의 결제의 `failNext()`로 만든다.

## 실패와 수정

- 구현 뒤 실패한 테스트는 없었다(처음 구현으로 대상 67개와 백엔드 전체가 통과).
- **결정 기록의 원인 설명을 확인해 고쳤다.** 결정 0151의 근거에 되돌림 5(b)(사용자 행 잠금 제거 + 기록을 처리 끝에 저장)의 500 원인을 처음에는 "끝의 INSERT가 유니크 제약에 걸림"으로 적었다.
  변형 코드를 다시 읽으니 끝의 INSERT는 `ON CONFLICT DO NOTHING`이라 실패하지 않고, 이미 있는 먼저 요청의 기록에 응답을 채우려다 `IdempotencyRecord.complete`의 확인에 걸릴 것이었다.
  그 변형을 다시 돌려 로그에서 '이미 응답을 저장한 멱등 기록이다'(4건)를 확인한 뒤 문구를 고쳤다. #55에서 배운 '되돌림 결과는 실제로 돌려 본 것만 적는다'를 적용했다.

## 규칙 테스트 되돌림 확인

운영 코드(필요하면 아직 병합되지 않은 V5 마이그레이션)의 한 부분을 잠시 바꾸고 해당 테스트 클래스를 돌린 뒤 git으로 되돌렸다. 매번 `git diff`로 운영 코드가 커밋과 같은지 확인했다.
모두 1회 실행이다(5(b)는 원인 확인을 위해 한 번 더 돌렸고 같은 결과였다).

| 2. `holdId` 비교 제거(늘 저장한 응답) | R5 다른 선점 400, 404 저장, 409 저장, 오류 표 3번의 자리. 4개 |

| 3(b). 3(a) + 상태 CHECK 제거 | R5 400 미저장(기록이 1개 남음), 스키마 '상태는 201·402·404·409만'. 2개 |

| 6(b). (사용자, 키) 유니크 제약 제거 | `ON CONFLICT`가 맞는 제약을 찾지 못해 모든 결제가 500: R5 API 테스트 11개, 스키마 유니크. 12개 |

`./scripts/verify.sh` 전체 통과(하네스, 백엔드 단위 149개·통합 298개, 프론트엔드. E2E는 아직 없어 SKIP). 같은 사용자가 같은 키로 다시 보내면 저장한 응답(상태 코드와 본문)을 그대로 받고,

## 배운 점

- 멱등성 테스트는 '같은 응답'만 보면 다시 처리한 경우를 놓친다. 다시 처리하면 결과가 달라지는 상황을 테스트가 먼저 만들어야 한다. 되돌림 1에서 409 테스트만 통과한 것이 그 예다.
- DB 제약과 응용 코드가 같은 것을 막으면, 한쪽만 되돌리는 확인은 통과할 수 있다(8(a)). 되돌림 결과를 적을 때 무엇이 대신 막았는지까지 적어야 테스트가 약한 것인지, 방어가 두 겹인 것인지 구별된다.
