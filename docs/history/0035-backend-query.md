# #35 백엔드 조회: 공연 목록·상세 API, 공연장별 좌석 배치, 공연·좌석 시드

- 기간: 2026-11-27 ~
- Issue: [#35](https://github.com/Rasit-NP/curtain-call/issues/35), PR: [#37](https://github.com/Rasit-NP/curtain-call/pull/37)
- 관련 결정: [0046](../decisions/0046-venue-seat-layout.md)~[0050](../decisions/0050-performance-detail-id-errors.md)

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 2단계(조회) 백엔드다. 1단계(인증 R6, #27·#28)가 끝났고,
프론트엔드 조회 화면(#36)과 동시에 진행한다. 고치는 폴더는 `backend/`와 `docs/`뿐이고, 결정 파일 번호는 0046~0059를 쓴다(#36은 0060부터).

보안 설정은 #27에서 `GET /api/performances/**`를 이미 공개로 열었다. 이 Issue는 보안 설정을 고치지 않는다.

## 진행 순서

1. 테스트를 먼저 썼다: 공연 목록·상세 API와 R6 공개 경로(`PerformanceApiTest`), 좌석·배치 DB 제약(`SeatSchemaTest`), 시드(`PerformanceSeedTest`).
   테스트 데이터는 엔티티를 거치지 않고 SQL로 만드는 도우미(`TestPerformances`)로 넣었다. API 테스트가 엔티티 매핑까지 함께 검증하고, 구현 전에도 컴파일돼 실패를 볼 수 있다.
2. 구현 전에 실행해 새 테스트 29개가 실패하는 것을 확인했다(테이블 없음, 경로 없음으로 404). 기존 `E2eProfileAuthTest` 5개는 시드 실행을 공통 도우미(`SeedFiles`)로 옮긴 뒤에도 통과했다.
3. 마이그레이션(`V2__`), 엔티티, 조회 서비스, 컨트롤러를 넣어 API·제약 테스트를 통과시켰다.
4. '시작 시각이 같으면 id 오름차순' 테스트가 실제로 정렬 기준을 잡는지 확인했다. id가 작은 공연을 나중에 고쳐 저장 순서를 id 순서와 다르게 두었고,
   정렬에서 `p.id`를 잠시 빼자 실패했다(복구함).
5. 시드(`V1001__` 공연장·배치, `V1002__` 공연·좌석)를 넣어 시드 테스트를 통과시켰다.
6. R6 되돌림 확인: 보안 설정에서 `GET /api/performances/**` 공개를 잠시 빼자 'R6: 공연 목록과 공연 상세는 토큰 없이 200이다'가 `401`로 실패했고, 복구하자 통과했다.
7. `./scripts/verify.sh` 전체 통과(백엔드 단위 50개, 통합 113개, 프론트엔드, 하네스. E2E는 아직 없어 SKIP).
8. 실제 앱 확인: 빈 임시 PostgreSQL에 `local` 프로필로 띄우자 Flyway가 스키마와 시드를 넣었고, `curl`로 목록(공연 3개), 상세(배치대로의 격자), 400·404 응답을 확인했다.
   사용 중인 compose DB는 건드리지 않았다.

## 판단과 근거

사람이 정한 것(2026-11-27, 메인 세션 대화, Issue 본문 '이미 정한 정책'):

- 좌석 배치는 공연장마다 다르고, 통로와 빈자리까지 표현한다([0046](../decisions/0046-venue-seat-layout.md)).
- 좌석 응답 `Seat`에 `gridRow`·`gridColumn`(1부터 셈)을 더한다. `row`·`number`는 표시 이름으로 그대로 둔다([0047](../decisions/0047-seat-grid-position.md)).
- 시드의 구체 값은 샘플 데이터이고 사람에게 묻지 않는다.

에이전트가 정한 것:

- **DB 구조**([0048](../decisions/0048-venue-performance-schema.md)): 공연 좌석은 공연을 만들 때 공연장 배치를 복사한다(스냅샷).
  배치를 참조하는 구조도 생각했지만, 판매된 좌석의 이름·위치가 배치 변경에 끌려가지 않아야 하고, 완료 조건(같은 공연에서 이름·위치 고유)을
  좌석 테이블의 유니크 제약 두 개로 바로 보장할 수 있어 복사를 골랐다. 대신 '공연 좌석 = 공연장 배치'는 DB가 보장하지 않아 시드 테스트로 확인한다.
  `row`는 SQL 키워드라 컬럼을 `seat_row`로 두고, row 오름차순이 DB 로캘에 따라 달라지지 않게 `COLLATE "C"`를 붙였다.
- **시드 값**([0049](../decisions/0049-performance-seed.md)): 세로 통로가 있는 40석 공연장과, 양 끝 빈자리·가로 통로가 있는 30석 공연장. 공연은 3개(첫 공연장 2회차).
  좌석은 모두 `AVAILABLE`이다. 선점·예매 없이 `HELD`·`SOLD`를 두면 좌석을 잡은 선점이 없는 상태가 되기 때문이다.
  시드 테스트는 값이 아니라 spec 2.5 최소 조건과 Issue가 정한 성질만 본다.
- **잘못된 performanceId**([0050](../decisions/0050-performance-detail-id-errors.md)): spec 6.3은 '정수가 아님'만 400으로 정했다.
  0·음수는 정수라 404, long 범위 밖은 경로 값 형식 오류(spec 3.1, 결정 0012)라 400으로 두었다. 공통 처리기의 기존 처리 그대로이고 새 코드를 만들지 않았다.
- **조회 구조**: 서비스는 공연장을 함께 읽은 엔티티를 넘기고, 컨트롤러가 record DTO로 바꾼다. open-in-view를 꺼 두었으므로 공연장은 fetch join으로 읽는다.

## 실패와 수정

- R6 되돌림 확인의 첫 실행이 `401`이 아니라 `ExceptionInInitializerError`로 실패했다. 원인은 Testcontainers가 Ryuk(정리용 컨테이너)에 연결하지 못한
  일시적인 Docker 문제였다(`Could not connect to Ryuk`). 테스트 결과가 아니므로 같은 확인을 다시 실행했고, 이번에는 기대대로 `401`로 실패했다.

## 배운 점

- 정렬 테스트에서 '같으면 id 순'은 데이터를 id 순서대로 넣으면 정렬 기준이 빠져도 우연히 통과한다. 저장 순서를 id 순서와 다르게 만들어야 기준이 빠졌을 때 실패한다.
