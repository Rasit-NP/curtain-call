# #29 작업 방식 규칙과 메인 체크아웃 수정 차단 훅

- 기간: 2026-11-26
- Issue: [#29](https://github.com/Rasit-NP/curtain-call/issues/29), PR: [#30](https://github.com/Rasit-NP/curtain-call/pull/30)
- 관련 결정: [0026](../decisions/0026-issue-creation-scope.md), [0027](../decisions/0027-issue-per-worktree-session.md), [0028](../decisions/0028-instruction-scope.md), [0029](../decisions/0029-guard-main-checkout-hook.md), [0030](../decisions/0030-guard-undecidable-input.md)

## 배경

2026-11-26, 1단계(인증)를 준비하던 중 에이전트가 같은 종류의 실수를 세 번 했다. 루트 `CLAUDE.md` '환경 개선'("같은 종류의 실수가 두 번 나오면 원인과 개선안을 `chore` PR로 제안한다")에 따라 이 Issue를 만들었다.

## 일어난 일 (시간 순서)

1. **Issue를 너무 많이 만들었다.** 사람이 "현재 진행해야 하는 작업을 이슈로 등록하라"고 했는데, 에이전트가 로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 남은 단계 전부(13개, #14~#26)를 만들었다. 사람이 지적해 모두 삭제하고, 1단계만 #27·#28로 다시 만들었다.
   - **#14~#26이 빈 이유**: GitHub Issue는 지워도 번호를 다시 쓰지 않는다. 그래서 이 저장소의 Issue 번호는 #13 다음이 #27이다.
2. **Issue를 별도 세션에서 진행하지 않았다.** #27·#28 작업 지시를 받은 에이전트가 메인 체크아웃에서 직접 구현하려 했다. 사람이 "하위 워크트리를 생성해서 하라"고 바로잡았다. 그 전의 #5·#6은 각각 별도 세션과 워크트리(`.claude/worktrees/`)에서 진행했었다.
3. **지시하지 않은 행동을 했다.** 사람이 "앞으로 알아서 잘 하도록 하는 방법을 제시하라"고 했는데, 에이전트가 제안하지 않고 세션부터 띄웠다. 지시하지 않은 세션 시작을 두 번 취소당했다.

## 원인

- 지시를 글자 그대로 따르지 않고 에이전트의 해석으로 넓혔다("현재 작업" → 로드맵 전체, "방법을 제시" → 바로 실행).
- 저장소 규칙에 'Issue 등록 범위'와 'Issue 작업은 별도 세션에서'가 없어, 새 세션마다 같은 판단을 다시 했다. #5·#6은 워크트리에서, #27·#28은 메인 체크아웃에서 하려 한 것이 그 예다.
- 에이전트의 개인 메모리는 그 컴퓨터의 에이전트 세션에만 적용되므로 저장소 규칙을 대신하지 못한다.

## 판단과 근거

**사람이 정한 것**(대화에서 지시, Issue #29 본문):

- 루트 `CLAUDE.md` '작업 흐름'에 세 규칙을 둔다: 지시 범위([0028](../decisions/0028-instruction-scope.md)), Issue 등록 범위([0026](../decisions/0026-issue-creation-scope.md)), Issue별 세션([0027](../decisions/0027-issue-per-worktree-session.md)).
- 규칙만으로는 같은 실수를 다시 할 수 있으니, `Edit`·`Write`·`NotebookEdit`로 메인 체크아웃 파일을 고치는 것을 `PreToolUse` 훅으로 막는다([0029](../decisions/0029-guard-main-checkout-hook.md)). 메인 워크트리는 경로가 아니라 git으로 판단한다. Bash로 쓰는 것은 막지 못한다는 한계를 기록한다.

이 Issue 자체도 새 규칙대로 진행했다. 메인 세션이 시작한 별도 세션이 git 워크트리(`.claude/worktrees/` 아래)에서 구현해 PR까지 만들었다.

**에이전트가 정한 것**([0030](../decisions/0030-guard-undecidable-input.md)):

- 대상 경로를 알 수 없는 입력은 막지 않는다. Claude Code는 항상 경로를 넘기므로, 파싱 문제 하나로 모든 수정이 막히는 쪽이 더 나쁘다고 봤다. Bash 우회로가 이미 있어 막는 쪽으로 기울어도 얻는 것이 작다.
- '이 저장소'의 메인 워크트리만 막는다. `CLAUDE_PROJECT_DIR`과 git-common-dir이 같은 저장소다. 사람이 다른 저장소의 수정을 지시한 경우까지 막지 않기 위해서다.
- 상대 경로는 입력의 `cwd` 기준, jq가 없으면 sed로 읽는다. 훅이 환경에 따라 조용히 꺼지지 않게 하기 위해서다.
- matcher가 `Read`·`Bash`까지 잡지 않는지도 테스트한다. 넓으면 메인 세션이 파일을 읽지도 못한다.
- `CLAUDE.md`의 'Issue별 세션'에 "워크트리의 브랜치 이름도 위 2번을 따른다"를 덧붙였다. 새 규칙이 아니라 기존 2번을 다시 가리킨 것이다. 앱이 만든 워크트리 브랜치는 `claude/...`로 시작해, 이 세션도 처음에 `chore/29-agent-workflow-rules`로 이름을 바꿔야 했다.

## 실패와 수정

- 하네스 테스트 6개를 먼저 쓰고, 훅이 없어 6개 모두 실패(종료 코드 127)하는 것을 확인한 뒤 훅을 만들었다.
- 구현 직후 코드를 다시 읽다가, 입력의 `cwd`가 상대 경로(슬래시 없음)이면 '가장 가까운 기존 상위 폴더'를 찾는 반복이 끝나지 않는 것을 찾았다. Claude Code가 보내지 않는 입력이지만, 훅이 멈추면 도구 실행이 시간 제한까지 묶인다. 슬래시가 없으면 현재 폴더로 판단하게 고치고, 잘못된 입력 테스트에 그 경우를 넣었다.
- 테스트가 결함을 잡는지 확인하려고 훅을 8가지로 잠시 고장 내고 하네스를 돌렸다. 모두 하나 이상의 테스트가 실패했고, 원래대로 복구했다.
  - 링크된 워크트리 판단 제거(경로만으로 판단), 다른 저장소 판단 제거, 가장 가까운 상위 폴더 대신 바로 위 폴더, 상대 경로를 현재 폴더 기준으로, 노트북 경로 읽기 제거, sed 대체 경로 고장, matcher를 `.*`로, 막을 때 종료 코드 1.
- 실제 저장소에서도 확인했다. 메인 체크아웃의 `CLAUDE.md`와 아직 없는 `docs/new.md`는 막히고(2), 이 워크트리의 파일, 에이전트 메모리, 스크래치패드는 통과했다(0). 프로젝트 폴더가 메인 체크아웃일 때와 워크트리일 때 모두 같았다.

## 결과

PR [#30](https://github.com/Rasit-NP/curtain-call/pull/30)을 열었다(병합 전). `./scripts/verify.sh` 전체 통과(harness PASS, 백엔드·프론트엔드 PASS, e2e는 `e2e/package.json`이 없어 SKIP). 하네스 테스트는 12개에서 18개가 됐다.

사람이 정할 것으로 남긴 것: git이 무시하는 메인 체크아웃 파일(`.claude/settings.local.json` 등)을 예외로 둘지([0029](../decisions/0029-guard-main-checkout-hook.md)), 'Issue를 진행하라'는 지시가 PR 생성까지 포함하는지 문구를 더 정할지([0028](../decisions/0028-instruction-scope.md)), 판단할 수 없는 입력을 막지 않는 선택을 받아들일지([0030](../decisions/0030-guard-undecidable-input.md)).

## 배운 점

- 에이전트의 해석으로 지시를 넓히면, 되돌릴 수 없는 결과(지운 Issue 번호)가 남는다.
- 에이전트의 개인 메모리는 저장소 규칙을 대신하지 못한다. 반복되는 판단은 저장소(`CLAUDE.md`, 훅)에 둬야 모든 세션이 같은 기준을 쓴다.
- 링크된 워크트리가 메인 체크아웃 폴더 안에 있어, '어느 체크아웃인가'는 경로가 아니라 git에 물어야 한다.
