# #42 프론트엔드 좌석 선택 화면(R1·R2·R6): 좌석 격자, 4석 선택, 선점 요청

- 기간: 2026-11-27 ~
- Issue: [#42](https://github.com/Rasit-NP/curtain-call/issues/42), PR: [#43](https://github.com/Rasit-NP/curtain-call/pull/43)
- 관련 결정: [0080](../decisions/0080-frontend-seat-selection-human.md), [0081](../decisions/0081-frontend-seat-selection-recommended.md), [0082](../decisions/0082-frontend-seat-selection-impl.md)

## 배경

로드맵 [#13](https://github.com/Rasit-NP/curtain-call/issues/13)의 3단계(선점) 프론트엔드다. 좌석 선택 화면(`/performances/:performanceId`)을 만든다. 좌석을 1~4석 고르고 '좌석 선택 완료'로 한 번에 선점한다(명세 1장).
2단계(#36)의 공연 목록 항목이 이 화면으로 링크하지만, 지금은 라우터 기본 404 화면으로 간다.
1단계(#28)의 인증 가드와 `401 AUTH_REQUIRED` 공통 처리, 2단계의 `useLoad`·`LoadStatus`·형식 함수를 그대로 쓴다.
백엔드 선점 생성(#41)이 다른 세션에서 동시에 진행되므로, 공연 상세(6.3)와 선점(6.4) API는 MSW로 흉내 낸다.

## 진행

- 메인 세션이 Issue를 만들고 이 Issue용 워크트리 세션을 시작했다. 브랜치는 `origin/main`에서 만든 `feat/42-frontend-seat-selection`이다.
- Issue의 '아직 정하지 않은 정책' 7개와, 명세·Issue를 읽으며 찾은 화면 동작 질문을 구현 전에 이 세션에서 사람에게 한 번에 물었다.

## 구현 중 판단과 근거(에이전트)

- **API 함수**: `getPerformance`(`auth: false`)와 `createHold`(`auth: true`)를 만들고 응답 타입 `Seat`, `PerformanceDetail`, `Hold`를 더했다. 공연 번호는 주소에서 받은 문자열 그대로 보내되 `encodeURIComponent`로 경로 한 칸에만 들어가게 했다. 숫자가 아니면 서버가 400을 준다.
- **MSW 핸들러**: 공연 상세 핸들러는 다른 공연 번호면 404, 선점 핸들러는 토큰이 없으면 401을 주고 받은 본문을 쌓는다. 기본 핸들러는 여전히 두지 않는다(0025).
- **표시 이름 함수**: `seatName`을 `src/format.ts`에 두고 내 예매의 `formatSeats`도 이것을 쓴다. 사람이 정한 명세 변경이라 내 예매 테스트의 기대값(`A-1, A-2` → `A1, A2`)을 먼저 바꾸고 실패를 확인한 뒤 고쳤다.
- **공연마다 새 화면, 409 뒤 다시 불러오기**([0082](../decisions/0082-frontend-seat-selection-impl.md)): 라우트 요소가 공연 번호를 `key`로 화면을 새로 만들어 0065의 남은 점(`load`가 바뀌어도 로딩으로 돌아가지 않음)을 피했다. 다시 불러오기는 로딩으로 돌아가지 않고 실패해도 격자를 남겨야 해서 `useLoad` 밖에서 화면이 직접 한다.
- **다시 불러오는 동안도 막기**([0082](../decisions/0082-frontend-seat-selection-impl.md)): 7번 '응답이 올 때까지 막는다'의 응답 처리에 409 뒤 다시 불러오기도 넣었다. 그 사이의 격자는 지난 상태라, 고른 좌석이 이미 잡힌 좌석일 수 있기 때문이다.
- **409를 받자마자 비우기**: 사람의 답은 '비운다'를 다시 불러오기 결과에 걸지 않았다. 그래서 다시 불러오기가 실패해도 고른 좌석은 빈 채다. 9번 질문의 '실패하면 격자와 선택을 그대로'는 그때 추천이 '나머지 선택은 남긴다'여서 쓴 문장이다.
- **격자 위치 검증**: jsdom은 배치를 계산하지 않으므로 버튼의 `grid-row`·`grid-column`과 격자의 `grid-template-*`를 검사한다. 먼저 jsdom이 이 속성을 읽는지, 값이 다르면 `toHaveStyle`이 실패하는지(헛통과하지 않는지) 작은 테스트로 확인했다.
- **새 라이브러리 없음**.

## 실패와 수정

- **테스트를 먼저 쓰고 실패 확인**: API 함수 테스트(함수 없음 3개, 모듈 없음 1파일), 표시 이름 테스트 3개(형식 2, 내 예매 1), 좌석 선택 화면 테스트 31개(화면 없음)가 실패하는 것을 확인한 뒤 구현했다.
- **워크트리에 의존성이 없음**: 처음 테스트를 돌렸을 때 `@vitejs/plugin-react`를 찾지 못했다. 새 워크트리라 `node_modules`가 없었다. `npm ci`로 설치했다.
- **타입 오류**: `formatSeats`의 매개변수를 `Pick<SeatRef, 'row' | 'number'>[]`로 넓혔더니, 형식 테스트가 넘기는 객체 리터럴의 `id`가 초과 속성 오류가 됐다. `Seat`도 `SeatRef`에 구조적으로 맞으므로 원래 타입(`SeatRef[]`)으로 되돌렸다.
- **기존 테스트 1개가 가드에 걸림**: 공연 목록의 '항목 링크를 누르면 그 경로로 간다'가 `/login`으로 갔다. 좌석 선택 화면이 생겨 그 경로가 가드 아래 실제 화면이 됐기 때문이다. 토큰과 공연 상세 핸들러를 더하고, 위치뿐 아니라 그려진 좌석 선택 화면을 기다리게 했다(0065). 기대값(`/performances/7`)은 바꾸지 않았다.
- **안정성 확인**: 되돌림 확인 전에 프론트엔드 전체 테스트를 15번 돌려 모두 통과했다. 그래서 아래 되돌림 결과의 실패는 불안정함이 아니라 되돌린 코드 때문이다.
- **R1·R2·R6 되돌림 확인**: 모든 변경을 커밋한 뒤 한 곳씩 되돌려 좌석 선택 화면 테스트(31개, 필요하면 API 테스트 포함)를 돌리고, 파일을 `git checkout`으로 복구했다. 실패한 테스트는 모두 되돌린 동작을 검사하는 것이었다.
  - R1: 선점됨·판매됨도 고를 수 있게 하면 3개(선택 불가 좌석, 409 뒤 다시 불러오기, 모두 팔린 공연), 409 뒤 다시 불러오지 않으면 2개, 409 뒤 고른 좌석을 비우지 않으면 2개가 실패했다.
  - R2: 4석 제한을 없애면 3개(5번째 좌석, 문구 지우기 두 개), 한도 초과도 선택을 비우고 다시 불러오게 하면 1개가 실패했다.
  - R6: 좌석 선택 화면을 가드 밖에 두면 1개, 공연 상세에 토큰을 붙이면 2개(API, 화면), 선점 요청에 토큰을 붙이지 않으면 4개(API 2개, 화면 2개. 토큰 없이 보낸 요청의 `AUTH_REQUIRED`는 지금 토큰과 달라 공통 처리를 하지 않으므로(0043) 401 테스트도 실패), `AUTH_REQUIRED` 공통 처리를 부르지 않으면 1개가 실패했다.

## 리뷰

PR [#43](https://github.com/Rasit-NP/curtain-call/pull/43)을 만든 뒤 이 세션에서 `/code-review high`로 리뷰했다(서브에이전트 없이, 지적 검증 단계 없이). 코드를 쓴 세션이 직접 한 리뷰라 독립 리뷰는 아니다. 머지 전에 고칠 결함은 없었고, 사소한 지적 6개가 나왔다.

- 결정 0060·0062·0064가 아직 좌석 형식을 `A-1, A-2`로 적고 있다. 0080이 바꿨는데 대체 표시가 없다.
- R1·R2 처리를 검증하는 테스트 3개의 이름에 규칙 번호가 없다(409 뒤 다시 불러오기, 문구 지우기, 모두 팔린 공연).
- 범례 견본의 `border` 축약형이 상태 클래스의 테두리 색을 덮어, 견본 테두리가 좌석과 다르다.
- `201` 뒤 이동하는 `/holds/{id}`에 아직 화면이 없어 라우터 기본 404 화면이 뜬다(Issue 범위대로 4단계).
- 선점 요청의 `AUTH_REQUIRED` 때 로그인 화면으로 가기 전에 '로그인이 필요합니다.'가 잠깐 보인다(PR #38에서 넘긴 지적과 같은 동작).
- 격자 크기 테스트가 인라인 스타일 문자열(`repeat(2, `)을 검사한다.

사람이 "고칠 것만 고치기"라고 지시해, 에이전트가 고칠 것을 골랐다.

- 고침: 결정 0080에 0060·0062·0064의 어느 부분이 바뀌었는지 적었다(바뀐 것은 좌석 형식뿐이라 원래 파일 상태는 그대로). 테스트 3개 이름에 `R1:`·`R2:`를 붙이고 대응표에서 R1·R2 행으로 옮겼다. 이 셋은 되돌림 확인 때 이미 실패한 테스트다(모두 팔린 공연은 R1a, 다시 불러오기는 R1b·R1c, 문구 지우기는 R2a). 견본은 `border` 축약형 대신 두께와 모양만 정했다. 격자 크기 테스트에는 인라인 스타일을 보는 이유(jsdom은 배치를 계산하지 않고, 명세 5장이 CSS Grid 값을 계약으로 정함)를 주석으로 적었다.
- 고치지 않음: `/holds/{id}`의 404 화면은 Issue가 4단계로 미룬 결제 화면이다. `AUTH_REQUIRED` 문구가 잠깐 보이는 것은 사용자가 겪는 동작을 바꾸는 일이라 정책 결정이고, PR #38에서 넘긴 같은 지적의 처리 Issue가 아직 정해지지 않았다.
- 고친 뒤 `./scripts/verify.sh` 전체를 다시 통과했다. 견본 테두리 색은 브라우저에서 눈으로 확인하지 않았다(CSS 우선순위로 판단).

## 배운 점

- 사람의 답이 명세나 다른 Issue와 맞지 않으면(선점이 멱등하다는 전제) 답대로 구현하지 않고, 어디가 다른지 근거와 함께 다시 묻는다. 사람은 바로잡힌 내용을 보고 다시 골랐다.
- 질문에 쓴 용어('안내 문구')가 명세 용어여도 사람에게는 낯설 수 있다. 화면에서 어떻게 보이는지 예를 들어 묻는 편이 빠르다.
- jsdom에서 스타일을 검사할 때는 그 속성을 jsdom이 읽는지, 틀린 값이면 실패하는지 먼저 확인한다. 지원하지 않는 속성이면 검사가 헛통과할 수 있다.
